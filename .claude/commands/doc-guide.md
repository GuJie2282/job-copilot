# 功能开发文档生成指南

## 📖 概述

本指南说明如何在开发完功能后,自动生成两份标准文档:
1. **API接口文档** - 给前端开发人员使用
2. **功能设计文档** - 给后端开发、维护和复用使用

## 🚀 快速开始

### 方式1: 使用Claude Code自动生成

当完成功能开发后,执行以下步骤:

1. **准备文档模板** (已完成✅)
   - API接口文档模板: `.claude/commands/api-template.md`
   - 功能设计文档模板: `.claude/commands/functional-design.md`

2. **开发功能时告诉Claude**
   在开发功能时,明确说明:
   ```
   请帮我开发 [功能名称] 功能，并在开发完成后生成标准文档：
   - API接口文档（给前端）
   - 功能设计文档（给后端维护）
   ```

3. **Claude会自动生成文档**
   开发完成后,Claude会:
   - 读取代码结构
   - 提取接口信息
   - 分析业务逻辑
   - 填充模板内容
   - 生成两份文档

### 方式2: 手动生成文档

如果需要手动生成文档,按以下步骤操作:

#### 步骤1: 收集信息

```bash
# 1. 找到功能相关的Controller文件
find . -name "*Controller.java" | grep [功能关键词]

# 2. 找到Service文件
find . -name "*Service*.java" | grep [功能关键词]

# 3. 找到Mapper文件
find . -name "*Mapper.java" | grep [功能关键词]
```

#### 步骤2: 使用Claude填充模板

告诉Claude:
```
我需要为以下功能生成文档:

功能名称: [XXX]
相关文件:
- Controller: [文件路径]
- Service: [文件路径]
- Mapper: [文件路径]

请帮我生成:
1. API接口文档（基于 .claude/commands/api-template.md）
2. 功能设计文档（基于 .claude/commands/functional-design.md）
```

## 📋 文档生成检查清单

### API接口文档必须包含的内容

- [ ] 变更历史表
- [ ] 基础URL（开发/测试/生产）
- [ ] 通用请求头说明
- [ ] 通用响应格式
- [ ] 通用错误码
- [ ] 所有接口的详细说明（地址、方法、参数、响应示例）
- [ ] 前端对接示例（Vue3/React）
- [ ] TypeScript类型定义
- [ ] 常见问题FAQ

### 功能设计文档必须包含的内容

- [ ] 文档信息表
- [ ] 变更历史表
- [ ] 功能概述（背景、目标、范围、用户角色）
- [ ] 需求分析（功能需求、非功能需求、业务约束）
- [ ] 业务流程（正常流程、异常流程、状态机）
- [ ] 系统设计（架构、模块、类设计、时序图）
- [ ] 数据库设计（表结构、SQL脚本）
- [ ] 接口设计
- [ ] 核心代码实现（关键方法、线程池配置、工具类）
- [ ] 技术方案（并发、事务、外部服务集成）
- [ ] 异常处理（异常分类、处理流程、错误码）
- [ ] 性能优化（优化策略、性能监控）
- [ ] 测试方案（单元测试、集成测试、性能测试）
- [ ] 部署说明（配置项、部署步骤、回滚方案）
- [ ] 影响分析（对现有功能、其他模块、数据库、性能的影响）
- [ ] 后续扩展（已知限制、未来优化、扩展点）
- [ ] 附录（术语表、参考文档、代码路径、联系人）

## 📂 文档存储规范

### 目录结构

```
docs/
├── design/
│   │   └── [模块名]/
│   │          ├── [功能]_api.md                  # API文档副本
│   │          ├── [功能]_DESIGN_DOC.md           # 功能设计文档

模块名
pressure/laboryatory/system/infra/member
```

### 文档命名规范

| 文档类型             | 命名规范                 | 示例                              |
|----------------------|--------------------------|-----------------------------------|
| API接口文档          | [功能]_api.md               | API_DOC.md                        |
| 功能设计文档         | [功能]_design.md            | DESIGN_DOC.md                     |

### 文档内容规范

1. **代码路径**: 使用项目根路径相对路径
   ```
   正确: tz-module-pressure/.../controller/...
   错误: D:\project-file\yudao-cloud\...\controller
   ```

2. **接口路径**: 使用完整的接口路径
   ```
   正确: /pressure/task-order/batch-sign
   错误: batch-sign
   ```

3. **表名**: 使用完整的表名
   ```
   正确: tz_task_order_item_report
   错误: task_order_item_report
   ```

4. **字段名**: 使用驼峰命名（Java）或下划线命名（数据库）
   ```
   Java: signStatus
   数据库: sign_status
   ```

## 🔄 文档更新流程

### 场景1: 新功能开发

```
需求分析 → 设计文档 → 代码实现 → 更新设计文档 → 生成API文档 → 提交代码
```

### 场景2: 功能修改

```
接收需求 → 修改代码 → 更新设计文档 → 更新API文档 → 提交代码
```

### 场景3: Bug修复

```
发现Bug → 定位问题 → 修复代码 → 更新设计文档（如需） → 提交代码
```

## 💡 最佳实践

### 1. 文档与代码同步

**推荐做法**:
- 在代码commit之前,先更新文档
- 文档作为Code Review的一部分
- 如果文档和代码不一致,拒绝合并

**检查方式**:
```bash
# 检查是否有对应的文档
find . -name "*Controller.java" -exec bash -c 'controller=$(basename {}); docpath=$(dirname {} | sed 's|controller|controller/xxx/vo|'); if [ ! -f "$docpath/API_DOC.md" ]; then echo "缺少文档: $controller"; fi' \;
```

### 2. 文档版本管理

**推荐做法**:
- 文档与代码一起提交到Git
- 在文档中记录变更历史（版本号、时间、修改内容、修改人）
- 重大变更时,在文档中更新"变更历史"表

### 3. 文档内容精确性

**推荐做法**:
- 从代码中提取接口信息,而不是手动编写
- 使用真实的请求/响应示例
- 包含完整的字段说明和类型定义

### 4. 文档可读性

**推荐做法**:
- 使用图表（流程图、时序图、状态机图）
- 提供代码示例
- 使用表格展示结构化信息
- 使用emoji标注重要信息（✅ ❌ 🟢 🟡 🔴）

### 5. 文档实用性

**推荐做法**:
- 包含前端对接示例（Vue3、React、TypeScript）
- 包含常见问题FAQ
- 包含性能测试结果
- 包含部署和回滚方案
