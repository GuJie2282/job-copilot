# 📝 功能开发文档生成 - 快速参考

## 一句话说明

开发功能时,告诉Claude: **"请帮我开发XXX功能,并生成API文档和设计文档"**,开发完成后Claude会自动生成两份标准文档。

---

## 🚀 快速使用

### 方式1: 开发新功能时自动生成 (推荐)

**复制以下提示词**:

```
请帮我开发 [功能名称] 功能,并在开发完成后生成标准文档:

## 功能需求
[简要描述功能需求]

## 功能要点
1. [核心功能点1]
2. [核心功能点2]
3. [核心功能点3]

## 文档要求
开发完成后,请生成以下文档:
1. API接口文档（基于 .claude/commands/api-template.md）
2. 功能设计文档（基于 .claude/commands/functional-design.md）

文档应包含:
- 完整的接口说明（地址、参数、响应示例）
- 前端对接示例（Vue3、React、TypeScript）
- 业务流程图和时序图
- 核心代码实现说明
- 性能优化和测试方案
- 影响分析

请开始开发。
```

### 方式2: 代码已完成,需要补文档

**复制以下提示词**:

```
我已经完成了 [功能名称] 的代码开发,现在需要生成文档。

## 相关代码文件
- Controller: [Ctrl+F搜索到的Controller文件路径]
- Service: [Ctrl+F搜索到的Service文件路径]
- Mapper: [Ctrl+F搜索到的Mapper文件路径]

## 数据库表
- 主表: [表名]

请基于以下模板生成文档:
1. API接口文档模板: .claude/commands/api-template.md
2. 功能设计文档模板: .claude/commands/functional-design.md

请分析代码,提取接口信息,并生成完整的文档。
```

## 🎯 文档质量标准

### 优秀文档的特征

✅ **完整性**: 包含上述所有检查清单项
✅ **准确性**: 接口信息从代码中提取,不是手动编写
✅ **实用性**: 包含前端对接示例和FAQ
✅ **可读性**: 使用图表、表格、代码示例
✅ **及时性**: 与代码同步更新

### 文档不合格的例子

❌ 只有接口列表,没有请求/响应示例
❌ 没有前端对接示例
❌ 没有业务流程图和时序图
❌ 没有性能测试数据
❌ 没有影响分析

## 📋 开发流程建议

### 推荐流程 (文档与代码同步)

```
1. 需求分析
   ↓
2. 编写设计文档初稿 (DESIGN_DOC.md)
   ↓
3. 代码实现
   ↓
4. 完善设计文档 (补充实际实现细节)
   ↓
5. 生成API文档 (API_DOC.md)
   ↓
6. Code Review (检查文档和代码一致性)
   ↓
7. 提交代码 + 文档
```

### 不推荐的流程

```
❌ 先写代码,后补文档
❌ 只写代码,不写文档
❌ 文档和代码不一致
❌ 文档信息过时
```

## 💡 提示词技巧

### 明确要求示例

**好的提示词**:
```
请帮我开发批量签名功能,并生成标准文档。

## 功能需求
- 支持批量选择1-100个报告进行签名
- 与Grape City服务集成
- 返回详细的签名结果（成功/失败列表）

## 技术要求
- 使用CompletableFuture并发处理
- 每个报告签名在独立事务中
- 记录签名日志

## 文档要求
生成以下文档:
1. API接口文档（包含Vue3、React、TypeScript示例）
2. 功能设计文档（包含流程图、时序图、性能测试数据）
```

**不好的提示词**:
```
❌ 开发一个批量签名功能
❌ 帮我写个文档
❌ 生成API文档（太模糊）
```

### 告诉Claude代码位置

**好的做法**:
```
相关代码文件:
- Controller: tz-module-pressure/.../AppApiTaskOrderController.java (行100-150)
- Service: tz-module-pressure/.../TaskOrderExpandServiceImpl.java (行200-300)
- Mapper: tz-module-pressure/.../TaskOrderItemReportMapper.java
```

**不好的做法**:
```
❌ 代码在Controller里
❌ 你自己找吧
```

## 🔄 文档更新时机

### 必须更新文档的情况

- ✅ 新增接口
- ✅ 修改接口（请求参数、响应字段）
- ✅ 修改业务逻辑
- ✅ 修改数据库表结构
- ✅ 优化性能（更新性能数据）
- ✅ 修复重大Bug（更新影响分析）

### 可以不更新文档的情况

- ⚠️ 代码重构（不改变功能）
- ⚠️ 修复小Bug（不影响接口和业务逻辑）
- ⚠️ 优化注释
- ⚠️ 调整代码格式

**建议**: 即使是小改动,也建议在文档中记录变更历史。


**解决方案**:
```
请参考以下文档的格式:
- [参考文档路径]
- [另一个参考文档路径]

调整当前文档的格式和风格。
```

### 问题3: 文档内容与代码不一致

**解决方案**:
```
请重新分析以下代码文件:
- [Controller路径]
- [Service路径]

更新文档中的接口信息,确保与代码一致。
```

## 🎯 总结

### 核心要点

1. **开发功能时**,明确要求Claude生成文档
2. **文档位置**: Controller包内的`vo/`目录或`resources/api/`目录
3. **两份文档**: API接口文档（前端）+ 功能设计文档（后端）
4. **质量标准**: 完整、准确、实用、可读
5. **同步更新**: 代码和文档一起提交
