# Proposal: 长耗时 LLM 任务的流式管线

## Why（为什么需要）

### 当前痛点

求职 Copilot 的三条核心链路——**简历解析、简历优化、JD 匹配**——都依赖单次同步 HTTP 请求承载多段 LLM 调用。随着任务变重（长简历、多轮迭代、深度模型），同步请求的"等待墙"问题在三个模块上先后爆发：

1. **简历解析**：一次请求要跑完"PDF 解析 → 质量检测 → LLM 提取整份画像 → 置信度计算"。主力档（glm-4.5）对长简历单次提取容易超过 LLM 自身超时阈值，触发重试，三次尝试累计耗时超过前端请求超时，用户等近三分钟后看到"请求失败"——既没结果，也没反馈。
2. **简历优化**：路径 A 自动生成最多跑三轮"生成 → 评估"迭代（最坏约六次 LLM），全部串行塞在一个请求里，靠前端 300 秒超时兜底；期间用户只看到与后端真实阶段无关的"假进度"轮播。
3. **JD 匹配**：评分链已升级为流式，但 Gap 增补（隐性偏好判断 + 建议生成，两段主力档 LLM）仍是同步请求，60 秒超时——同一类定时炸弹，只是尚未频繁引爆。

这三处本质是同一个问题：**把"多段、慢、可能失败"的 LLM 流程压进一个同步请求，任何一段慢或超时，整条请求就被拖垮，且用户全程无感知**。

### 产品价值

**流式管线**把"一次性等结果"变成"边跑边反馈"，一举解决三个层面的问题：

1. **可用性**：持续向客户端推送进度，连接保持活跃，从根本上消除请求超时墙——任务再慢也不会以"请求失败"收场。
2. **体验**：用户实时看到"正在解析 PDF → AI 提取画像中 → 生成简历草稿 → 六维评估"，等待从"黑盒干等"变成"可观测的进度"。简历优化还能逐字呈现生成内容（打字机效果），与主流 AI 产品的体验对齐。
3. **质量（顺带根治）**：简历解析借此从"一次提取整份画像"重构为"分段提取"——每段 LLM 上下文更聚焦、输出更短更准，从源头缓解"项目名称错位"等结构化提取错误。

### 战略定位

这是项目从"功能可用"迈向"体验可靠"的关键基建。求职是高焦虑场景，用户对"卡住、没反应、失败"的容忍度极低；流式反馈把每一次长耗时操作都变成"看得见在推进"的体验，是留存与信任的基础。同时，统一的流式管线为后续所有 LLM 重任务（如复盘报告、面经扩充）提供可复用的模式。

## What Changes（做什么变更）

### 新增能力

1. **streaming-pipeline（流式管线）**
   - 长耗时 LLM 任务以增量方式持续向客户端推送进度与结果，取代单次同步请求
   - 连接保活：任务执行期间持续下发事件，消除请求超时墙
   - 阶段进度：每个处理阶段完成即推送真实进度（取代前端模拟进度）
   - 分段结果：结构化任务按段推送中间结果（如画像逐段成型）
   - 增量内容：自由文本任务逐字推送生成内容（如简历打字机生成）
   - 可取消：客户端可在任意时刻中止进行中的任务
   - 错误降级：任意阶段失败以错误事件收尾，已产出的部分结果不丢失

### 落地能力（既有能力的流式化改造）

2. **简历解析（user-profile 的提取环节）**
   - 提取流程从"一次 LLM 提取整份画像"重构为"分段提取"（基本信息 / 教育 / 工作经历 / 项目 / 技能等分段）
   - 每段以独立 LLM 调用完成，单段上下文聚焦、输出短、准确率高，且天然成为流式进度分段点
   - 每段 LLM 调用以增量方式输出，连接持续活跃
   - 画像结构由"扁平平行数组"调整为"嵌套对象数组"，从源头消除字段错位
3. **简历优化（resume-optimization）**
   - 路径 A 自动生成：按图节点（准备 → 生成 → 评估 → 校验 → 导出 → 落库）推送阶段进度；生成环节逐字输出简历内容
   - 路径 B 精修：每轮改写逐字输出，配合既有 interrupt 机制
4. **JD 匹配（jd-matching 的增补环节）**
   - Gap 增补（隐性判断 + 建议生成）并入匹配主请求的流式通道，用户提交一次 JD 即可看到"评分 → 增补"全流程，不再依赖独立的同步增补请求

### 系统变更

- **公共流式基础设施（新增）**：
  - 后端：统一的 SSE 事件组装工具（从 JD 模块内联实现抽取为公共组件）
  - 前端：统一的 SSE 消费封装（fetch + ReadableStream 解析，从 JD 模块抽取为公共工具）
  - 前端开发环境：流式端点直连后端（绕开开发代理对流式响应的不支持）
- **LLM 调用方式扩展**：服务层新增"增量输出"调用方式（stream），与既有同步调用并存；按任务输出性质选用
- **API 变更**：
  - 简历解析新增流式端点（POST，text/event-stream），既有同步端点保留兼容
  - 简历优化 generate / refine 切换为流式响应
  - JD 匹配 match 端点延长事件流至增补完成
- **简历提取结构变更**：画像内"工作经历 / 项目经验"等由扁平平行数组调整为嵌套对象数组，前端展示与编辑组件同步适配
- **超时策略变更**：前端不再为长耗时任务设置"覆盖整个流程"的大超时，改为依赖流式保活 + 连接级超时

## Capabilities（能力清单）

### streaming-pipeline（流式管线）

**能力描述**：为长耗时 LLM 任务提供统一的增量输出通道，使任务执行过程对客户端可观测、可取消、不超时。

**核心行为**：
```
客户端发起任务（POST，text/event-stream）
  → 服务端持续推送事件：
      stage    —— 阶段进度（{message, node?}）
      segment  —— 分段中间结果（结构化任务，如画像的一段）
      token    —— 增量文本内容（自由文本任务，如简历草稿）
      done     —— 任务完成（最终结果）
      error    —— 任务失败（错误码 + 文案，已产出部分保留）
      （执行期间持续保活，无内容时下发心跳）
  → 客户端可随时取消（AbortController）
```

**输出性质决定流式粒度**：
- 自由文本输出（简历 Markdown）→ token 级（逐字打字机）
- 结构化输出（画像 JSON、Gap JSON）→ 段级 / 阶段级（半截结构无法渲染，整段完成后下发）

## Impact（影响分析）

### 用户体验影响

**正面影响**：
- 三条核心链路不再出现"长时间等待后请求失败"
- 全程可见真实进度，等待焦虑显著降低
- 简历优化逐字生成，体验对齐主流 AI 产品
- 客户端可主动取消跑偏的任务

**潜在风险**：
- 流式过程中网络抖动导致连接中断 → 缓解：已产出的段/阶段结果在前端可见，中断后可基于已落库的部分结果续作或重试
- 用户看到中间结果误以为已完成 → 缓解：进度与最终结果在视觉上明确区分（进度态 vs 完成态）

### 技术影响

**依赖复用**：SSE 基础设施已在 JD 匹配落地（`graph.astream` + `StreamingResponse` + 前端 fetch 流式解析），本变更将其公共化并推广到其余模块，无需引入新依赖。

**性能影响**：
- 流式保活使前端请求超时墙失效，任务总耗时不变但不再因超时失败
- 简历解析分段提取：单段 LLM 更快更准，但总 LLM 次数增多（一次 → 多段），端到端总耗时可能与单次相当或略增，换取准确率与流式体验
- 简历优化 token 流：首字节时间大幅提前（用户几秒内看到简历开始生成），体感耗时显著下降

**架构影响**：
- 形成"按输出性质选择流式粒度"的统一模式（token / 段 / 阶段），成为后续所有 LLM 重任务的范式
- 简历提取结构嵌套化，画像数据模型与前端展示/编辑组件同步演进
- 公共 SSE 工具成为横切基础设施

### 开发影响

**工作量估算**：
- 公共流式基础设施（后端 SSE 工具 + 前端 SSE 封装 + 开发环境直连配置）：1 天
- 简历解析（分段提取重构 + 嵌套结构 + 流式端点 + 前端适配）：3-4 天
- 简历优化（generate 流式 + token 输出 + refine 流式 + 前端真实进度）：2-3 天
- JD 匹配增补并入主流：1 天
- LLM 增量调用改造 + 超时/重试策略调整：1 天
- 测试与打磨（多样本、中断恢复、降级）：2 天
- **总计：10-12 天**

**技术风险**：
- 增量 JSON 输出无法边收边渲染结构化结果 → 缓解：结构化任务按段整体下发，仅自由文本任务用 token 级
- 流式与既有 interrupt（简历优化路径 B）结合需处理暂停语义 → 缓解：路径 B 单独设计，跨请求维持状态
- 简历提取结构变更需前后端联动 → 缓解：结构变更与流式改造在同一变更内同步完成
- 开发代理不转发流式响应 → 缓解：流式端点直连后端，已在 JD 匹配验证

## Success Criteria（成功标准）

### 功能验收
- [ ] 简历解析：上传 / 粘贴后持续看到阶段进度，完成后收到结构化画像，全程无"请求失败"
- [ ] 简历解析：分段提取后，工作经历 / 项目经验的字段不再错位（项目名、职责、描述正确对应）
- [ ] 简历优化：路径 A 生成时逐字呈现简历内容，阶段进度真实反映后端节点
- [ ] 简历优化：路径 B 精修逐字输出改写内容
- [ ] JD 匹配：提交 JD 后，评分与 Gap 增补在同一流式通道内连续完成
- [ ] 客户端可在任务进行中取消
- [ ] 任意阶段失败时，已产出的段 / 阶段结果在前端保留，并以错误事件明确提示

### 质量验收
- [ ] 长简历、多轮迭代等重任务下，连接持续活跃，不触发前端请求超时
- [ ] 自由文本任务首字节时间显著早于整体完成时间
- [ ] 流式过程中断后，已落库的部分结果可被后续读取

### 用户体验验收
- [ ] 三条链路全程有可读的进度反馈，无"黑盒干等"
- [ ] 简历优化生成有打字机效果
- [ ] 进度态与完成态视觉区分清晰
