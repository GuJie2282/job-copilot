# Design: 模拟面试（mock-interview）

## 设计原则

1. **会话而非任务**：前三个模块（画像/JD/简历）是"一次性任务"，模拟面试是"长程会话"。所有架构决策围绕"如何让状态机支持中断、恢复、循环"展开。
2. **追问是灵魂**：真实面试与题库 App 的分水岭是"基于回答的动态深挖"。追问必须高质量、可控、可解释——不靠面试官 LLM 临场自由发挥。
3. **诚实的技术判断**：RAG、向量检索等新技术只用在真正创造价值（面经库数据飞轮）的地方，不为用而用；不在 LLM 自己能搞定的地方堆料。
4. **承上启下的飞轮**：消费画像 + JD/Gap（承上），产出面经库沉淀（启下），面经库又反哺出题——闭环即壁垒。
5. **沉浸与教学的显式权衡**：实战模式（不实时评分，保沉浸）与教练模式（实时提示，保学习）分离，用模式切换而非别扭折中。

---

## 核心设计决策

### 决策 1：长程对话架构（interrupt 中断与恢复）

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 外层循环：每轮重新 invoke 整个子图 | 实现最简单 | 状态散落、历史靠 prompt 重传、追问逻辑难表达 | 不选 |
| LangGraph `interrupt`：子图内部暂停等输入 | 状态机原生、状态由 checkpointer 保住、分支逻辑用边表达 | 首次使用、有学习成本 | ✅ 选择 |
| 脱离 graph：纯对话表 + while 循环 | 最直白 | 放弃状态机价值、与前序模块风格不一致 | 不选 |

**最终选择**：LangGraph `interrupt` 机制

**理由**：面试的本质是"人机轮流"的长程流程，需要状态机能"在某节点挂起、等人类输入、再恢复"。`interrupt` 正是为此设计——节点内调用 `interrupt(value)` 挂起并把 value 返回调用方，调用方下次用 `Command(resume=user_input)` 唤醒，图从断点继续。状态由 checkpointer 保住，可跨请求、抗重启。追问/换题/结束的分支用条件边表达，比 if-else 干净。

**权衡**：项目首次使用 interrupt，存在未知。缓解：阶段 1 先做最小 spike 验证可行性（de-risk）。但这个"首次"本身就是面试讲点——用状态机做了别人用裸循环做不到的事。

### 决策 2：会话状态持久化（独立 checkpointer 文件）

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| MemorySaver（现状） | 已有 | 重启即丢，面试 30 分钟中途后端重启就崩 | 不选 |
| SqliteSaver，独立文件 | 零运维、原生支持、与业务库隔离 | 多一个文件 | ✅ 选择 |
| SqliteSaver，复用业务库 | 少一个文件 | 会话过程数据与业务档案数据混在一起 | 不选 |
| PostgresSaver | 生产级 | MVP 过重、要起服务 | 不选 |

**最终选择**：SqliteSaver，独立 `interview_checkpoints.db` 文件

**理由**：模拟面试引入项目**第三种存储需求**——会话状态（面试进行到哪、transcript、临时题库）。它与业务数据（画像/JD/面经，跨会话长期资产）、对话记忆（通用 chat，临时）职责不同。会话状态是"过程数据"（一次面试的生命周期），独立文件便于清理/迁移，不污染业务档案库。

**权衡**：多一个 .db 文件。但分层清晰带来的可维护性收益更大。

**三层存储分层**：
```
① 业务数据（SQLite 业务表）：画像、JD匹配、面经 —— 跨会话长期资产
② 会话状态（SqliteSaver，独立文件）：面试进度、transcript、临时题库 —— 一次面试的生命周期
③ 对话记忆（MemorySaver）：通用 chat 多轮上下文 —— 临时
```

### 决策 3：出题输入归一化（有/无 JD 双模式）

**最终选择**：出题第一步把可变输入归一为统一的"出题上下文"，题库生成器只认统一结构。

```
有 JD 定向：画像 + 求职目标 + job_profile(JD四分类) + gaps + 公司面经库检索
无 JD 通用：画像 + 求职目标(job_target) + 画像强弱项分析 + 行业面经库检索
                              ↓
                    统一出题上下文 → 题库生成器
```

**理由**：JD 非必要——很多人想练面试但手里没具体 JD。无 JD 时用画像的求职目标岗位 + 画像强弱项（经历丰富的深挖、薄弱的考察）+ 行业 RAG 实现定向，而非泛泛题库。

**权衡**：无 JD 模式下"考查重点"从 Gap 清单替换为画像强弱项分析，出题上下文结构需兼容两种来源。State 中 `jd_result_id` 设为可选。

---

### 决策 4：QuestionPackage 考查包结构（追问地图预埋）⭐

**最终选择**：每道题不是一段文本，而是结构化"考查包"，**出题时即预埋追问地图与评判标尺**。

```
QuestionPackage {
  category,              // 题型
  intent,                // 出题意图
  stem,                  // 主问题
  anchor,                // 个性化锚点（画像中的经历依据）
  jd_ref,                // 关联 JD 哪条（无 JD 时空）
  probing_points: [],    // ⭐ 可挖掘点（追问弹药，出题时预埋）
  ideal_signals: [],     // ⭐ 好回答应体现的信号（评判标尺）
  estimated_minutes,     // 预估耗时（喂给问答计划）
  rag_source             // 来源标签（数据治理）
}
```

**理由**：这是本设计最重要的决策。追问质量是面试真实感的命门。若让 evaluator LLM 每轮"凭感觉"决定追问什么，结果飘忽、难调、不可解释。改为**出题时预埋两张地图**——evaluator 只做"信号差检测"：回答缺哪个 ideal_signal，就沿对应 probing_point 追问（按图索骥）。这让追问可控、可调优、可回溯，评分也有依据（信号命中率）。

**权衡**：出题阶段多生成两个字段，prompt 更复杂。但换来追问的可解释性——这个权衡是值得的，且是核心面试讲点。

---

### 决策 5：追问的信号差检测（按图索骥）

**最终选择**：evaluator 用回答比对 ideal_signals，依据"信号差"决定动作。

| 回答情况 | 判定 | 动作 |
|----------|------|------|
| 命中全部 ideal_signals | 已充分 | 换题 |
| 缺 1-2 个信号且有对应 probing_point | 有挖掘点 | 追问该方向 |
| 回答空洞/跑题 | 兜底 | 追问"能具体讲讲吗？" |

**追问上限**：每题最多 3 次（`current_q_probes` 计数）。追问到终点（probing_points 耗尽 ∨ 计数到 3 ∨ 回答已充分）自动换题。

**理由**：把"是否追问、追问什么、何时停"三个问题都落到**可计算的信号差**上，而非 LLM 主观判断。1-3 次的上限避免无限深挖导致的面试失衡。

**权衡**：信号命中判定本身依赖 LLM（回答是否体现了某信号），存在主观性。缓解：ideal_signals 在出题时具体化（如"量化结果"而非"讲得好"），降低判定模糊度。

---

### 决策 6：档位语义化 + 预设问答计划

**最终选择**：用语义化档位（简短/正常/深度/全程）替代时间隐喻，session_setup 阶段预生成"问答计划"。

| 档位（前端展示） | 问答计划（后端预生成） |
|------------------|------------------------|
| 简短 | 3-4 题，每题浅问（probing 上限 1），无反问 |
| 正常（默认） | 5-7 题，中问（probing 上限 2），可选反问 |
| 深度 | 7-10 题，深挖（probing 上限 3），含反问 |
| 全程 | 完整流程：破冰→各题型→反问 |

**理由**：文字面试没有真实时间流逝，"30 分钟"对用户是模糊隐喻。改为语义化档位——用户选的是"今天想练多深"，不是"我有几分钟"。结束判定从"时间到了"改为"问答计划执行完了"，干净。档位反向影响出题（题数、每题 probing_points 数量）。

**权衡**：档位与题数/深度的映射是经验值，需样本校准。

---

### 决策 7：复盘的改进范例（生成 ≠ 检索标准答案）

**最终选择**：复盘逐题提供 `better_version`——基于**用户自身回答**临场**生成**改进版示范。

**关键区分（产品判断精细度）**：
- ❌ 反对：从题库**检索**万能标准答案让用户背（培养依赖，违背练习初衷）
- ✅ 采用：基于用户回答**生成**个性化改进版（培养反思）

**理由**：同一个"给示范"动作，来源不同性质完全不同。题库检索的示范培养背诵，基于自身回答的改进版培养反思。不一刀切禁掉"示范"，而是区分来源——这是产品判断的精细度体现。

**权衡**：生成改进版多一次 LLM 调用。但这是复盘教学价值的核心，不可省。

---

### 决策 8：RAG 只用于面经库（诚实评估）

**最终选择**：RAG 在模拟面试场景只用于面经库（个人库 + 公司库），不滥用。

| RAG 用途 | 价值 | 判断 |
|----------|------|------|
| 个人面经库（沉淀+复用） | ★★★★★ | ✅ 采用，数据飞轮核心 |
| 公司/岗位面经库（真实感） | ★★★★ | ✅ 采用，冷启动混合策略 |
| JD 定制出题 | ★★★ | ⚠️ 锦上添花，LLM 直接出题已够 |
| 技术知识点校验 | ★★ | ❌ 不做，LLM 自己能判，过度设计 |
| 标准答案范例 | ★ | ❌ 不做，违背练习初衷（见决策 7） |

**理由**：RAG 的真正价值在"个性化面经复用"——这是产品壁垒（私有资产），且对齐差异化战略。其他场景要么 LLM 自己能搞定（堆料减分），要么有害（标准答案）。能讲清"哪里该用、哪里不该用"比"用了 RAG"更重要。

**权衡**：放弃部分"技术深度"展示机会。但克制本身是工程成熟度的体现。

---

### 决策 9：公司面经库冷启动（混合策略 + 来源治理）

**最终选择**：混合冷启动——手工精选种子打底 + LLM 扩充长尾 + UGC 逐渐替换，全程来源标签治理。

```
冷启动路径：
  ① 手工精选（human_curated）：3-5 岗位 × 10-20 真题，质量最高，演示用
  ② LLM 扩充（llm_generated）：基于种子 + 公开信息填补长尾岗位
  ③ UGC 替换（user_ugc）：随使用，真实面经逐渐顶替生成数据

检索优先级：human_curated > user_ugc > llm_generated
透明展示：前端标注"基于真实面经" vs "AI 拟题"
```

**理由**：公司面经库无现成数据源。爬取有合规风险（面试项目踩雷减分），纯 UGC 冷启动空库。混合策略兼顾质量、覆盖、合规。来源标签 + 透明度既是数据治理，也是面试讲点（不假装数据是真的）。

**权衡**：精选种子需人工投入（本身就是产品功夫）。生成数据真实性打折，但透明标注缓解。

---

### 决策 10：人设双维度（风格 × 角色）+ 压力面正交

**最终选择**：人设 = 风格维度（用户选）× 角色维度（系统配/用户选），压力面作为风格正交叠加。

```
Persona {
  tone: 严肃/轻松/风趣/温和/压力,    // 维度① 风格（用户选）
  role: {company, position, seniority},// 维度② 角色
  style_prompt,                        // 注入面试官 system prompt
  stress_mode                          // 压力开关（与题型正交）
}
```

**理由**：用户要"能挑风格"。拆成两个正交维度——风格影响语气口吻，角色影响提问专业性与背景。压力面本质是风格叠加（质疑、施压），与题型正交，故作为风格开关而非第 6 种独立题型，工作量可控。

**权衡**：预置人设组合（字节·PM·专业风趣 等）降低用户选择负担，但需精心设计。

---

### 决策 11：实战/教练双模式

**最终选择**：双模式分离——实战模式面试中不实时评分（沉浸），教练模式侧栏实时提示。

| 模式 | 行为 | 适合 |
|------|------|------|
| 实战（默认） | 面试官只问只追不评价，结束后才出复盘 | 体验真实压力 |
| 教练 | 每答完一题，侧栏悄悄给一句改进提示 | 边练边学 |

**理由**：真实面试官面无表情，中途评分破坏沉浸、诱导表演；但作为教练产品用户又想要即时指导。两种诉求冲突，用模式切换显式权衡，而非一个别扭折中。

**权衡**：教练模式的实时提示增加每轮 LLM 调用。但这是模式开关，默认实战不增成本。

---

### 决策 12：会话式 API + 多态响应

**最终选择**：会话式 API（创建/答题/续面/复盘），答题端点采用多态响应。

```
POST /api/interview/sessions          创建会话 → session_id + 第一题
POST /api/interview/sessions/{id}/answer  提交回答 → 下一题 OR 结束信号
GET  /api/interview/sessions/{id}     查状态/transcript（续面）
GET  /api/interview/sessions/{id}/debrief  获取复盘
GET  /api/interview/sessions          历史会话

answer 响应多态：
  {status:"awaiting_answer", round, question, coach_hint?}  // 继续
  {status:"finished", total_rounds, debrief_id}             // 结束
```

**理由**：现有 API（如 `POST /api/jd/match`）是一次性请求-响应。面试是"开个会话、多次回合、最后收尾"，需全新范式。多态响应符合"一次回答推动状态机前进一步"的语义，前端逻辑聚合。

**权衡**：多态响应前端需按 status 分支。但比分离端点（/next-question + /finish）更贴合状态机心智。

---

### 决策 13：向量库与检索选型

**最终选择**：Chroma（向量库）+ BGE（嵌入）+ 混合检索（BM25 关键词 + 向量语义）。

**理由**：
- Chroma：纯 Python、本地文件、零运维，MVP 够；不选 Pinecone/Qdrant（过重，面试项目减分）
- BGE：中文表现好、开源可本地，省成本
- 混合检索：面试题含大量专业术语，纯向量召回不稳，关键词检索兜底

**权衡**：混合检索实现比纯向量复杂。但召回稳定性是 RAG 可用性的前提。

### interrupt 时序图（一轮面试的完整生命周期）

```
请求1: POST /sessions（创建）
  └─ 图跑: session_setup(出题+装配人设+生成问答计划)
     → interviewer 提问 → interrupt(question)
     → checkpointer 存盘(thread_id=session_id)
     → 返回: {status:"awaiting_answer", question, round:1}

      ⏳ 用户思考作答（可跨小时，checkpointer 撑得住）

请求2: POST /sessions/{id}/answer {answer}
  └─ Command(resume=answer) 唤醒图(同 thread_id)
     → evaluator 评估(信号差检测+评分+写transcript)
     → route_round 决策
        ├─ probe/next → 回 interviewer → interrupt(下一题) → 返回 awaiting_answer
        └─ end        → debrief(生成报告+写个人面经库) → 返回 {status:"finished", debrief_id}

请求3(可选): GET /sessions/{id}/debrief → 获取复盘报告
请求4(可选): GET /sessions/{id} → 续面/查看 transcript
```

```
                                        ├─ 信号差检测(ideal_signals)
                                        ├─ 评分 + 写 transcript
                                        └─ route_round

3. 追问 / 下一题
                     ◀──────────────  probe / next → interviewer
                                        └─ interrupt(下一题)

4. 计划执行完
                     ──────────────▶  反问环节 → debrief
                                        ├─ 逐题回顾 + 改进范例
                                        ├─ 卡壳分析 + 后续建议
                                        └─ 写入个人面经库(RAG)

5. 看复盘
   ◀──────────────  debrief 报告
```

## 与前后模块的集成（闭环接口）

### 承上：消费画像与 JD 匹配

```
user_profiles（画像快照）+ [可选] jd_match_results（job_profile + gaps）
   → 面试 session_setup → 个性化题库 + 问答计划

画像消费点：
  • work_descriptions / project_descriptions → 出题锚点（追问命根子）
  • job_target → 无 JD 模式的定向依据
  • 强弱项分析 → 考查重点

JD 匹配消费点（可选）：
  • job_profile 四分类 → 出题覆盖岗位要求
  • gaps → Gap 大的重点考
```

**关键约束**：`profile_ref` 用**快照而非引用**——面试开始时拷贝画像进 state，防止面试中画像被改导致不一致。

### 启下：产出面经库（数据飞轮）

```
debrief → archive_entry（结构化面经条目）→ 个人面经库（向量库）
   ↓ 下次面试
   出题检索："你上次这题答得不好，再练"
   复盘对比："这个考查点，三个月前 vs 现在"
```

**这是闭环最强讲点**：数据飞轮——用户越用，面经库越厚，出题越个性化，竞品抄不走。RAG 在这里是商业模式的一部分，不是技术装饰。

### 闭环调整
本变更不实现简历优化。Gap 清单的消费契约由本变更定义（作为出题考查重点），而非喂给简历优化。

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| interrupt 机制首次使用 | 阻塞主流程 | 中 | 阶段1先做最小 spike 验证可行性 |
| 追问质量不稳定 | 真实感崩塌 | 高 | 追问地图出题时预埋，evaluator 按图索骥 |
| 信号命中判定主观 | 追问/评分偏差 | 中 | ideal_signals 具体化（如"量化结果"），样本调优 |
| 档位节奏不合理 | 面试过长/过短 | 中 | 档位参数可配置，多样本校准 |
| 公司库冷启动数据不全 | 真实感打折 | 中 | 来源标签透明 + 精选种子打底 |
| 向量检索召回不稳 | 出题/复盘偏差 | 中 | 关键词 + 语义混合检索 |
| 长程会话状态丢失 | 续面失败 | 低 | SqliteSaver 持久化 + 独立文件 |
| LLM 调用失败/超时 | 流程中断 | 中 | 指数退避重试 + 友好降级 + 保留进度 |
| 单轮延迟较长 | 体验下降 | 中 | 分阶段进度提示 + 同步可接受 |

## 技术选型总结

| 层级 | 选择 | 理由 |
|------|------|------|
| 长程对话 | LangGraph `interrupt` + checkpointer | 状态机原生支持中断恢复 |
| 会话状态 | SqliteSaver（独立文件） | 零运维、与业务库隔离 |
| 追问机制 | 信号差检测（出题预埋地图） | 可控、可解释、可调 |
| 档位 | 语义化（简短/正常/深度/全程） | 去时间隐喻、内容计划驱动 |
| 复盘示范 | 基于自身回答生成改进版 | 培养反思非背诵 |
| RAG 范围 | 仅面经库（个人+公司） | 诚实评估，不滥用 |
| 公司库冷启动 | 混合（精选+生成+UGC）+ 来源治理 | 质量、覆盖、合规兼顾 |
| 人设 | 风格 × 角色双维度，压力正交 | 可挑风格，工作量可控 |
| 模式 | 实战/教练分离 | 沉浸与教学显式权衡 |
| API | 会话式 + 多态响应 | 贴合状态机心智 |
| 向量库 | Chroma + BGE + 混合检索 | 零运维、中文好、召回稳 |
| 框架 | LangGraph + FastAPI + Vue | 与现有栈一致 |

## 面试讲解要点

1. **为什么模拟面试比改简历难？**
   - 前三个模块是"任务"（一问一答），面试是"会话"（持续关系）
   - 会话需要状态机支持中断与恢复——这正是 LangGraph 选型的回报（interrupt + checkpointer）

2. **追问为什么不用 LLM 自由发挥？**
   - 追问质量是真实感命门，自由发挥会飘忽、不可解释
   - 出题时预埋"可挖掘点 + 理想信号"两张地图，evaluator 按图索骥（信号差检测）
   - 追问可控、可调优、可回溯

3. **为什么用语义化档位而不是"30 分钟"？**
   - 文字面试没有真实时间流逝，"30 分钟"是模糊隐喻
   - 用户选的是"练多深"不是"有几分钟"；结束由问答计划决定，干净

4. **RAG 为什么只用面经库？**
   - 面经库是产品壁垒（私有资产 + 数据飞轮），RAG 在这里创造真实价值
   - 技术知识点判错 LLM 自己够用，标准答案有害——克制是成熟度
   - 能讲清"哪里该用哪里不该用"比"用了 RAG"更重要

5. **复盘的"改进范例"和"标准答案"有何不同？**
   - 题库检索的标准答案培养背诵，基于自身回答的改进版培养反思
   - 同一个动作来源不同性质完全不同，不一刀切

6. **双模式解决了什么矛盾？**
   - 真实面试官面无表情（沉浸）vs 教练要实时指导（学习），两种诉求冲突
   - 用模式切换显式权衡，而非别扭折中

7. **公司面经库冷启动怎么解决？**
   - 爬取有合规风险（减分），混合策略（精选+生成+UGC）兼顾质量覆盖合规
   - 来源标签 + 透明度，不假装数据是真的——数据治理本身就是讲点

8. **数据飞轮怎么构成壁垒？**
   - 每场面试沉淀进个人面经库，越用越懂你，竞品抄不走
   - RAG 在这里是商业模式的一部分，不是技术装饰
