# Design: 简历解析与个人画像建立

## 设计原则

1. **多层防御，而非追求完美**：承认 PDF 解析和 LLM 提取都有失败率，通过多层检测 + 降级策略确保整体可用性
2. **透明度优先**：让用户知道解析过程的中间状态（文本预览、置信度），建立信任
3. **合理的取舍**：MVP 不支持 OCR（扫描件），提供降级方案（复制粘贴、手动填写）
4. **用户可纠错**：解析结果不是"黑盒"，用户可以查看和修正

---

## 核心设计决策

### 决策 1：文件解析技术选型

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| pdfplumber | 中文支持好，表格解析准确，API 简单 | 稍重 | ✅ 选择 |
| PyPDF2 | 轻量，安装简单 | 中文可能乱码，复杂排版支持差 | 备选 |
| PyMuPDF (fitz) | 性能最好 | 依赖外部 C 库，安装复杂 | 不选 |
| pdf.js（前端） | 减少后端压力 | 不稳定，浏览器兼容问题 | 不选 |

**最终选择**：主用 pdfplumber，备选 PyPDF2

**理由**：
- pdfplumber 对中文简历支持最好
- 有备选方案提高成功率
- 技术栈简单，面试能讲清选型逻辑

**权衡**：放弃 PyMuPDF 的性能优势，换取安装简单和稳定性

---

### 决策 2：是否支持 OCR（扫描件 PDF）

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 支持 OCR | 覆盖率 ↑ (70% → 90%) | 技术复杂度 ↑↑，OCR 可能出错，增加依赖 | 不选 |
| 不支持 OCR | MVP 简单，稳定 | 扫描件无法解析，需要降级方案 | ✅ 选择 |

**最终选择**：MVP 不支持 OCR

**理由**：
1. **MVP 应覆盖 80% 场景，不是 100%**：扫描件在真实场景占比 < 20%
2. **技术复杂度 vs 价值**：OCR 会引入新的出错点（识别错误、后处理）
3. **降级方案足够**：复制粘贴 + 手动填写可以覆盖扫描件场景
4. **产品取舍是加分项**：面试时能讲"合理的取舍"比堆砌技术更有价值

**权衡**：牺牲 15-20% 的覆盖率，换取技术简单度和稳定性

**未来扩展**：如果用户反馈显示扫描件占比高，再考虑加入 OCR（Tesseract 或 OCR API）

---

### 决策 3：文本质量检测阈值

**场景分析**：

```
质量分数 0.9-1.0：✅ 直接解析，无警告
质量分数 0.6-0.9：⚠️  解析，但显示警告
质量分数 0.4-0.6：❌ 解析，但强烈建议检查
质量分数 < 0.4：❌ 解析结果不可用，建议重新上传或复制粘贴
```

**最终选择**：0.6 作为关键阈值

**理由**：
- 0.6 以上：通常能提取到核心信息（姓名、教育、工作），置信度可接受
- 0.6 以下：文本结构混乱或内容过少，LLM 提取不可靠

**权衡**：阈值不是硬性规则，而是"建议用户检查"的提示线

---

### 决策 4：LLM 提取的 Prompt 策略

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 单一 Prompt（标准提取） | 简单 | 对低质量文本效果差 | 不选 |
| 双层 Prompt（高质量 + 容错） | 适应不同质量 | 需要质量分判断 | ✅ 选择 |
| Few-shot（给例子） | 提升准确率 | Token 消耗大，可能过拟合 | 可选 |
| JSON Schema 约束 | 输出格式稳定 | 部分模型不支持 | DeepSeek 支持 |

**最终选择**：双层 Prompt + JSON Schema 约束

**理由**：
- **双层 Prompt**：根据质量分数选择标准 Prompt 或容错 Prompt
- **JSON Schema**：用 Pydantic BaseModel + LangChain 的 `with_structured_output`，确保输出稳定
- **可选 Few-shot**：如果效果不理想，再加示例

**Prompt 设计**：

```python
# 标准提取（质量分 ≥ 0.8）
prompt = """
请从以下简历中提取结构化信息，输出 JSON 格式。
必须包含以下字段：{schema}

简历文本：
{text}
"""

# 容错提取（质量分 < 0.8）
prompt = """
以下简历文本可能存在质量问题（{issues}）。
尽管如此，请尽力提取信息。

容错规则：
1. 时间不明确 → 填"未知"
2. 信息找不到 → 填 null
3. 结构混乱 → 优先提取核心信息（姓名、教育、工作）
4. 宁可留空，不要编造

简历文本：
{text}
"""
```

**权衡**：双层 Prompt 增加复杂度，但显著提升低质量文本的提取效果

### 决策 5：置信度计算方法

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| LLM 自我评估 | 理解上下文 | LLM 可能过度自信 | 辅助 |
| 规则匹配（文本相似度） | 客观、可解释 | 无法处理语义变化 | ✅ 主用 |
| 混合（LLM + 规则） | 准确率高 | 复杂 | ✅ 最终选择 |

**最终选择**：混合方案

**实现逻辑**：

```python
def calculate_confidence(field_value: str, original_text: str) -> float:
    """
    计算字段置信度（百分比）
    """
    # 1. 精确匹配：95%
    if field_value in original_text:
        return 0.95
    
    # 2. 模糊匹配：85%（去除标点、空格）
    normalized_value = field_value.replace(" ", "").replace("-", "")
    normalized_text = original_text.replace(" ", "").replace("-", "")
    if normalized_value in normalized_text:
        return 0.85
    
    # 3. 关键词匹配：70%（部分匹配）
    value_words = field_value.split()
    match_count = sum(1 for word in value_words if word in original_text)
    if match_count / len(value_words) > 0.7:
        return 0.70
    
    # 4. 无法验证：50%（可能是 LLM 推断的）
    return 0.50
```

**权衡**：
- 精确匹配优先，避免过度自信
- 最低 50%（而不是 0%），因为 LLM 推断也有一定价值

### 决策 6：LangGraph 节点职责分离

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 单节点（file_parser + extraction） | 简单 | 职责不清晰，难以测试 | 不选 |
| 多节点（6 个节点） | 职责清晰，易测试，易扩展 | 复杂度高 | ✅ 选择 |

**最终选择**：多节点分离

**节点职责**：

```
router_node          → 判断输入类型（文件/文本）
file_parser_node     → 解析文件（PDF/docx → 文本）
text_validation_node → 验证粘贴文本
quality_check_node   → 评估文本质量
profile_extraction_node → LLM 提取画像
confidence_calc_node → 计算置信度
result_formatter_node → 格式化输出
```

**理由**：
- **职责清晰**：每个节点做一件事，易理解和测试
- **易扩展**：后续加新节点（如 OCR 节点）不影响现有节点
- **面试加分**：能讲"状态机的解耦优势"

**权衡**：复杂度增加，但 LangGraph 本身就是为复杂流程设计的

### 决策 7：State 字段设计

**字段分类**：

```python
class AgentState(TypedDict):
    # === 基础对话 ===
    messages: Annotated[list, add_messages]
    
    # === 输入相关 ===
    resume_source: str | None           # "file" | "text"
    resume_text: str | None             # 提取的文本
    resume_file_name: str | None        # 文件名（用于显示）
    
    # === 解析结果 ===
    user_profile: dict | None           # 结构化画像
    profile_confidence: dict | None      # 置信度（百分比）
    profile_quality_score: float | None # 文本质量分（0-1）
    
    # === 状态标记 ===
    parse_status: str | None            # "pending" | "success" | "warning" | "error"
    parse_warnings: list[str] | None     # 警告列表
    parse_error: str | None             # 错误信息
    
    # === 用户交互 ===
    awaiting_confirmation: bool         # 是否等待用户确认
    user_confirmed: bool | None         # 用户是否确认
```

**设计原则**：
- **职责分类**：输入、结果、状态、交互分开
- **可追溯**：保留 `resume_source` 和 `resume_file_name`，便于调试
- **状态标记**：`parse_status` 统一表示解析阶段的状态

**权衡**：
- 字段较多（15+），但每个都有明确用途
- 后续可根据实际使用精简

### 决策 8：同步 vs 异步 API

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 同步 API | 简单，前端易实现 | 用户等待时间长（5-10 秒） | ✅ MVP 选择 |
| 异步 API（task_id） | 用户体验好，可后台处理 | 复杂度高，需轮询或 WebSocket | v1 考虑 |
| 流式（SSE） | 实时反馈，体验最好 | 技术复杂度最高 | v2 考虑 |

**最终选择**：MVP 用同步 API

**理由**：
1. **MVP 优先简单**：同步 API 足够演示
2. **可接受的等待时间**：5-10 秒等待在演示场景可接受（加加载动画）
3. **后续可升级**：架构设计保留异步扩展空间

**用户体验优化**：
```javascript
// 前端加载动画
- "正在解析简历..." (0-2s)
- "正在提取画像..." (2-5s)
- "正在计算置信度..." (5-7s)
- "即将完成..." (7-10s)
```

**权衡**：牺牲用户体验（等待），换取实现简单

**未来升级**：如果用户反馈等待时间太长，再考虑异步或流式

---

### 决策 9：前端和后端职责边界

**选项对比**：

| 选项 | 前端职责 | 后端职责 | 优点 | 缺点 | 选择 |
|------|----------|----------|------|------|------|
| 方案 A | 上传文件 | 解析 + LangGraph | 前端简单 | 后端重 | 不选 |
| 方案 B | 解析文件 | LangGraph | 后端轻 | 前端复杂（pdf.js 不稳定） | 不选 |
| 方案 C | 上传 + 用户交互 | 解析 + LangGraph | 职责清晰 | 需两次 API 调用 | ✅ 选择 |

**最终选择**：方案 C（混合）

**职责划分**：

```
前端：
- 文件上传（FormData）
- 文本粘贴
- 文本预览（用户可编辑）
- 画像展示（置信度显示）
- 画像编辑（表单）
- 错误提示和引导

后端：
- 文件解析（PDF/docx → 文本）
- 文本质量检测
- LangGraph 调用
- LLM 提取
- 置信度计算
- 结果格式化
```

**交互流程**：

```
1. 用户上传文件 → POST /api/resume/parse-file
   → 后端解析 → 返回文本 + 质量分

2. 前端显示文本预览 → 用户编辑 → 点击"确认"

3. POST /api/resume/extract（传入文本）
   → 后端调用 LangGraph → 返回画像 + 置信度

4. 前端显示画像 → 用户编辑 → POST /api/resume/update-profile
```

**权衡**：需要两次 API 调用，但用户体验更好（可以预览和修改文本）

### 决策 10：错误处理策略

**错误分类**：

| 错误类型 | 示例 | 处理方式 | 用户引导 |
|----------|------|----------|----------|
| **致命错误** | 文件损坏、加密 PDF | 阻止继续 | 引导重新上传或复制粘贴 |
| **警告** | 文本质量差、部分字段缺失 | 允许继续 | 建议检查或手动修正 |
| **信息提示** | 文件过大但可解析 | 不阻止 | 轻量提示 |

**错误信息设计原则**：

```
❌ 不要：
"解析失败：Error 500"

✅ 应该：
"无法解析这个 PDF 文件

可能原因：
• 这是扫描件 PDF（图片格式）
• PDF 文件已加密
• 文件损坏

建议的解决方案：
1. 另存 PDF：在 Word 中"另存为"可搜索的 PDF
2. 复制文本：打开简历，全选复制，然后粘贴
3. 手动填写：直接填写个人画像表单

[复制文本] [手动填写] [查看帮助]"
```

**权衡**：错误信息较长，但用户友好，减少流失

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| PDF 解析失败率高 | 用户无法使用 | 中 | 多解析器备选 + 降级方案（复制粘贴） |
| LLM 提取准确率低 | 用户不信任 | 中 | 容错 Prompt + 置信度展示 + 用户修正 |
| 文件处理出错 | 用户体验差 | 低 | 临时文件清理 + 异常捕获 + 友好提示 |
| 性能问题（响应慢） | 用户流失 | 低 | 加载动画 + MVP 同步，v1 异步 |
| 真实简历格式多样 | 解析覆盖率不足 | 高 | 质量检测 + 用户预览 + 手动修正 |

## 技术选型总结

| 层级 | 技术选择 | 理由 |
|------|----------|------|
| PDF 解析 | pdfplumber（主）+ PyPDF2（备） | 中文支持好，有备选方案 |
| Word 解析 | python-docx | 官方推荐，稳定 |
| LLM 调用 | LangChain + DeepSeek | 结构化输出支持，成本低 |
| 框架 | LangGraph | 状态机驱动，易扩展 |
| API | FastAPI（同步） | MVP 简单，v1 升级异步 |
| 前端 | Vue 3 + Composition API | 与项目现有技术栈一致 |

## 面试讲解要点

1. **为什么不用 OCR？**
   - MVP 覆盖 80% 场景，不是 100%
   - 技术复杂度 vs 价值权衡
   - 降级方案（复制粘贴）足够

2. **为什么多层防御？**
   - 承认 PDF 解析和 LLM 都不是 100% 准确
   - 每一层都有价值：快速失败、质量检测、容错解析、用户确认
   - 这是工程思维，不是堆技术

3. **为什么显示置信度？**
   - 透明度建立信任
   - 用户知道哪些字段需要检查
   - 这是产品设计思维（以用户为中心）

4. **为什么 LangGraph？**
   - 状态机驱动，流程清晰
   - 节点解耦，易扩展
   - 可调试、可讲（面试加分）

5. **降级策略的价值？**
   - 不是所有用户都有完美 PDF
   - 提供多种路径：文件、粘贴、手动
   - 产品思维：考虑边界场景

### 决策 11：LLM 重试机制

**问题**：LLM 提取可能失败（置信度低）或超时

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 不重试 | 简单 | 成功率低 | 不选 |
| 固定重试 1 次 | 提升成功率 | 增加耗时（5-10 秒） | ✅ 选择 |
| 固定重试 3 次 | 成功率最高 | 耗时太长（15-30 秒） | 不选 |
| 智能重试 | 根据置信度决定 | 复杂 | v1 考虑 |

**最终选择**：MVP 用固定重试 1 次

**实现逻辑**：

```python
def profile_extraction_node(state: AgentState) -> dict:
    """
    LLM 提取画像，带重试机制
    """
    text = state.get("resume_text")

    # 第一次提取
    result = llm_extract_profile(text)
    confidence = calculate_confidence(result, text)

    # 如果置信度过低，重试一次
    avg_confidence = sum(confidence.values()) / len(confidence)
    if avg_confidence < 0.6:
        print(f"置信度过低（{avg_confidence:.2f}），重试中...")
        # 使用容错 Prompt 重试
        result = llm_extract_profile_robust(text)
        confidence = calculate_confidence(result, text)

    return {"user_profile": result, "profile_confidence": confidence}
```

**权衡**：重试增加耗时，但显著提升成功率

### 决策 12：超时处理

**问题**：LLM 调用可能超时（>30 秒）

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 无限等待 | 简单 | 用户可能认为卡住 | 不选 |
| 硬超时（30 秒） | 避免无限等待 | 丢失已提取的数据 | 不选 |
| 软超时 + 保留数据 | 用户体验好 | 需要保存中间状态 | ✅ 选择 |

**最终选择**：软超时（30 秒）+ 保留已提取的文本

**实现逻辑**：

```python
def extract_with_timeout(text: str, timeout: int = 30) -> dict:
    """
    带超时的 LLM 提取
    """
    try:
        # 设置超时
        result = llm_extract_profile(text, timeout=timeout)
        return {"status": "success", "profile": result}
    except TimeoutError:
        # 超时后返回部分结果
        return {
            "status": "timeout",
            "message": "提取超时，请稍后重试",
            "resume_text": text,  # 保留已提取的文本
            "suggestion": "文本已保存，可以重新提取"
        }
```

**权衡**：超时后保留文本，用户不需要重新上传

### 决策 15：进度指示设计

**问题**：解析过程需要 10-15 秒，用户不知道在做什么

// 前端模拟进度（基于时间的估算）
