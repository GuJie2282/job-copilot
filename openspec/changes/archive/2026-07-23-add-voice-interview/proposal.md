# Proposal: 模拟面试语音回答（add-voice-interview）

## Why（为什么需要）

### 当前痛点
模拟面试当前是纯文字输入，在"沉浸感"上存在明显短板：

1. **面试是"说"的，不是"打"的**：真实面试靠口语表达，文字输入把面试降格成"打字练习"。用户一边组织语言一边敲字，注意力被输入方式占据，无法还原真实的表达压力与思维节奏。
2. **文字引发自我审查**：打字可以反复删改、字斟句酌，但真人面试一句话说出口就收不回。文字模式让回答趋于书面化、过度修饰，掩盖了真实的口语水平与临场组织能力——而这恰恰是面试要练的核心。
3. **紧张感缺失**：真实面试的紧张来自"必须开口说"。文字模式完全没有这种压力，模拟的"脱敏"价值大打折扣。

### 产品价值
语音回答把模拟面试从"做题"拉回"面试预演"：

1. **沉浸感跃升**：用户开口说、面试官追问，逼近真实面试的对话节奏与心理压力，真正实现"预演脱敏"。
2. **暴露真实弱点**：口语表达才会暴露"嗯啊口癖、逻辑断裂、紧张卡壳"——这些在文字里被掩盖的弱点，正是面试要改的。语音让复盘有了更真实的素材。
3. **闭环体验完整**：模拟面试已具备"个性化出题 → 动态追问 → 结构化复盘 → 面经沉淀"全链路，语音是最后一块"真实感"拼图，让整个体验从"能用"升级到"想用、敢用、有用"。

### 战略定位
语音是**体验差异化**的放大器。市面上多数面试工具停在文字题库；本项目的动态追问已领先一步，语音进一步把"像真面试"做到位，强化"带记忆的全链路求职教练"定位。同时对齐项目一以贯之的"数据自持"哲学——语音识别本地部署，音频/文本不出服务器。

## What Changes（做什么变更）

### 新增能力
**mock-interview（模拟面试）能力增强——新增"语音回答模式"：**

- **模式选择**：面试配置时选择输入方式（文字 / 语音），语音为沉浸增强项，文字模式完整保留
- **全自动状态机收音**：收音跟随面试对话状态——面试官提问/思考时关闭收音，轮到用户回答时自动开启，无需用户手动控制起停
- **录音机式控制**：用户回答时支持暂停（避噪思考）、继续、手动结束提交，不设静默强制断句（保留思考空间）
- **沉浸式呈现**：消息流中用户回答以"语音条"呈现，不显示识别文字（避免自我审查）；支持长按回看识别文字（兼顾纠错）
- **麦克风权限降级**：权限拒绝或设备不支持时，自动降级文字输入并提示，不阻断面试
- **识别失败降级**：语音转写失败时，语音条标注失败并提供重试或切文字入口

### 系统变更
- **后端新增语音转写端点**：`POST /api/interview/voice/transcribe`，接收音频文件、返回识别文本。这是后端唯一新增，复用现有 multipart 上传基建
- **零侵入 Agent 链路**：语音识别结果以文本形式接入现有 `submitAnswer`，整个 LangGraph 面试子图、checkpointer、评估/追问/复盘链路完全不动；后端不感知回答来源是文字还是语音
- **前端输入层增强**：InterviewRoom 在语音模式下用录音控件 + 状态机收音替换文字输入框；InterviewSetup 新增输入方式选择
- **新依赖**：后端语音识别引擎（faster-whisper，MIT 开源，本地部署）

### 不做的事（明确边界）
- **不做 TTS（面试官语音播报）**：本次只做用户侧语音输入（STT），面试官问题仍以文字气泡呈现。TTS 涉及音色选择、回授消除（AEC）等独立复杂度，留作后续变更
- **不做流式实时识别**：采用"录完再识别"的批处理模式（用户手动结束触发），不边说边出字。流式需 WebSocket + VAD 静默检测，复杂度高且与"不显示文字"的沉浸诉求冲突
- **不持久化音频**：音频仅用于即时转写，转写后即弃；transcript 仍只存文本（后端无感于来源）

## Capabilities（能力清单）

### mock-interview 增强：语音回答模式
**能力描述**：模拟面试支持用户以语音方式回答，收音由面试对话状态机自动控制，识别结果以文本形式无缝接入现有答题链路，呈现上以语音条保持沉浸感。

**核心流程**：
```
配置面试时选择"语音"输入方式
  → 进入面试间（轮到用户回答时自动开启收音 + 指引"轮到你了"）
  → 用户开口回答（可暂停/继续，说完了手动结束）
  → 录音上传 → 后端 faster-whisper 转写 → 文本
  → 文本接入 submitAnswer（现有链路零改动）
  → 评估/追问/下一题（面试官"思考"期间收音关闭）
  → 消息流以语音条呈现（不显示文字，长按可回看）
```

**关键行为**：
- 收音跟随状态机：面试官说话时关、轮到用户时开
- 录音机式控制：自动开始、暂停、继续、手动结束
- 沉浸与回看平衡：默认不显示文字、长按可回看识别结果
- 全链路降级：权限拒绝 / 设备不支持 / 识别失败 → 文字模式兜底

## Impact（影响分析）

### 用户体验影响
**正面影响**：
- 沉浸感大幅提升，逼近真实面试的开口压力与对话节奏
- 暴露口语真实弱点（口癖、卡壳、逻辑断裂），复盘更有料
- 状态机自动收音 + 清晰指引，用户无需操心"何时开始/结束"，专注表达

**潜在风险**：
- 语音识别准确率非 100%（专业术语、口音）→ 缓解：可回看识别文字、识别失败可重试/切文字
- 麦克风权限弹窗打断首次体验 → 缓解：进入语音面试前明确引导"接下来需要使用麦克风"
- 识别有延迟（几秒）→ 缓解：状态栏明确提示"正在识别你的回答…"，管理预期

### 技术影响
**新机制引入**：
- 浏览器端音频采集（MediaRecorder API + getUserMedia，项目首次）
- 后端语音识别（faster-whisper 本地部署，项目首次引入 ASR）
- 前端状态机驱动的收音控制（收音跟随面试状态流转）

**架构亮点（零侵入）**：
- 语音是前端输入层增强，识别后以文本接入现有 `submitAnswer`
- 后端只加 1 个转写端点，整个 LangGraph 面试链路、checkpointer、评估/追问/复盘零改动
- 后端不感知回答来源；语音功能挂掉不影响文字面试——纯增量增强，风险隔离

**依赖复用**：复用现有 multipart 上传基建（resume.py 的 UploadFile 范式）、LLM 重试/降级哲学、Vue 前端框架与 IM 消息流组件。

**性能影响**：
- 语音转写（small 模型，CPU）：一段 15-30s 录音约 3-8 秒（实测验证）
- 不影响现有评估/追问/复盘的 LLM 时序（语音转写是答题前置步骤，与 LLM 链路串行不重叠）

**架构影响**：
- 不新增存储层（音频即时转写即弃，文本仍走现有 transcript）
- 不改变会话状态机（语音是输入层，checkpointer 状态结构不变）

### 开发影响
**工作量估算**：
- 后端：2-3 天（ASR 选型 spike 装包验证 0.5 天、转写端点 + 格式处理 1 天、降级与测试 0.5-1 天）
- 前端：4-5 天（录音基建 + 麦克风权限 1 天、状态机收音 + 指引 1.5 天、语音条 UI + 可回看 1 天、模式选择 + 降级 0.5-1 天）
- 测试与打磨：1-2 天（中文识别质量、降级链路、e2e）
- **总计：7-10 天**

**技术风险**：
- faster-whisper 在 Windows 的安装与模型下载（CTranslate2 wheel / HuggingFace 国内访问）→ 缓解：阶段 1 先做最小 spike 验证可行性（de-risk），失败则降级备选方案（Vosk 后端 / Whisper Web 前端）
- 录音格式（webm/opus）解码兼容性 → 缓解：spike 验证 faster-whisper 经 PyAV 直读 webm；不行则 pydub + ffmpeg 转 wav
- CPU 推理延迟 → 缓解：实测 small 模型延迟；过慢则降级 tiny/base 或提示用户

## Success Criteria（成功标准）

### 功能验收
- [ ] 面试配置可选择"文字 / 语音"输入方式
- [ ] 语音模式下，轮到用户回答时自动开启收音（面试官说话时关闭）
- [ ] 用户可暂停、继续、手动结束录音
- [ ] 录音上传后端转写为文本，文本接入现有答题链路（评估/追问/复盘正常）
- [ ] 消息流以语音条呈现用户回答，不直接显示识别文字
- [ ] 长按/点击语音条可回看识别文字
- [ ] 麦克风权限拒绝/设备不支持时，自动降级文字模式并提示
- [ ] 识别失败时，语音条标注失败并提供重试或切文字入口
- [ ] 文字模式行为完全不受影响（回归无副作用）

### 质量验收
- [ ] 中文识别质量可用（日常表达 + 常见专业术语识别准确率达标）
- [ ] 收音状态机跟随准确（面试官说话时不误收、轮到用户时不漏开）
- [ ] 语音转写延迟可接受（15-30s 录音 < 10s 出结果）
- [ ] 各降级路径完整（权限拒/不支持/识别失败均有兜底）

### 用户体验验收
- [ ] 用户能在面试前一键选择语音模式，无需复杂配置
- [ ] 全程有清晰指引（"轮到你了""正在聆听""正在识别""面试官正在思考"）
- [ ] 语音交互自然，无需用户操心收音起停
- [ ] 识别出错时可发现、可纠正（回看 + 重试/切文字）

## Timeline（时间线）

采用**先 de-risk 后铺开**策略——先验证最大技术风险（ASR 引擎能否在本地跑通），再铺前端体验。

**阶段 1：ASR spike 与转写端点（2-3 天）**
- faster-whisper 装包验证（Windows + 模型下载）
- 录音格式解码验证（webm/opus 直读 or 转码）
- 后端 `POST /voice/transcribe` 端点 + 降级
- → 产出：后端能接收音频文件、返回识别文本（可 curl 验证）

**阶段 2：前端录音基建与状态机收音（2.5 天）**
- MediaRecorder + 麦克风权限 + 录音/暂停/继续/结束
- InterviewRoom 状态机收音（跟随 currentQuestion/submitting）
- 底部状态栏指引文案
- → 产出：能在面试间里语音回答，识别文本接入答题链路

**阶段 3：语音条 UI 与模式选择（1.5 天）**
- MessageBubble 语音条变体（沉浸呈现 + 长按回看）
- InterviewSetup 输入方式卡片选择
- 麦克风降级（权限拒/不支持 → 文字）
- → 产出：完整语音面试体验，含配置入口与沉浸呈现

**阶段 4：测试与打磨（1-2 天）**
- 中文识别质量样本验证
- 降级链路验证
- e2e 自动化（语音模式主链路）

**总计：约 7-10 天**（阶段 1 为后端 de-risk，阶段 2-3 前端，阶段 4 收尾）
