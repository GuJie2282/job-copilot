# Design: 简历优化（画像驱动的简历生成与定制）

## 设计原则

1. **承上启下**：简历优化是全链路的兑现环节——消费画像 + Gap，产出可投递简历。Gap 结构是 JD 匹配与本模块的接口契约（已在 jd-matching design 决策 4 定义），本模块只兑现，不重新设计接口。
2. **生成而非润色**：输入永远是「结构化画像 + Gap」两个确定的东西，不接收用户的旧简历作为优化底稿。画像由简历解析环节建立并校验过置信度，是唯一可信的事实来源。
3. **双层质量门**：LLM 做内容评估（语义、主观判断），脚本做格式校验（确定性硬规则）。各司其职，稳定且可解释——沿用 JD 匹配"混合而非堆料"的原则。
4. **同构复用**：路径 A 与简历解析 / JD 匹配同构（流水线子图），路径 B 与模拟面试同构（interrupt + checkpointer 长程会话）。降低认知与维护成本。
5. **A 兜底、B 增强**：默认自动出活保证"一定有产出"，精修模式保留用户掌控感。两种模式共享生成、评估、导出的核心节点。

---

## 决策 1：交互模式 —— A+B 混合（默认自动 + 可选精修）

**选项对比**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 纯自动（A） | 生成→评估→自动迭代→导出，一次跑完 | 快、成本可控、实现轻 | 黑盒，用户无掌控；画像不足时无能为力 |
| 纯协同（B） | 每轮 interrupt 让用户参与 | 掌控感强、可挖亮点、教育价值 | 慢、成本不可控、实现重 |
| **A+B 混合** | 默认 A 出第一版，可选进入 B 精修 | 兼顾速度与掌控，B 复用 mock-interview 基建 | 两套机制都要建，工程量最大 |

**最终选择**：A+B 混合

**理由**：
- 简历生成天然是"先要快出一版，再决定精不精修"的场景。A 兜底保证任何情况下用户都拿得到一份 PDF，不会因为交互卡住而空手而归。
- B 的真正价值集中在两个场景：①画像不足需要追问挖亮点（这正是 amlei-resume skill 的灵魂能力——"不直接问你要改哪，要聊出来"）；②用户想精修一份重要的目标岗位简历。这两个场景值得支持，但不应强制所有用户走完。
- B 复用模拟面试已建好的 checkpointer + interrupt 基础设施（同构复用，设计原则 4），增量成本主要在简历领域的 prompt 与前端交互，而非底层机制。

**权衡**：两套模式都要实现，工程量最大。缓解：路径 A 在 Day 12 可先行交付 MVP，路径 B 作为 Day 13 起的增量，不阻塞核心闭环。

## 决策 2：生成 vs 优化 —— 只生成，不优化旧简历

**选项对比**：

| 方案 | 输入 | 优点 | 缺点 |
|------|------|------|------|
| 只优化 | 用户旧简历 + JD | 贴近"改简历"直觉 | 旧简历质量参差、格式各异，优化效果不可控；要先把旧简历解析回来，再区分"保留/改写"，复杂 |
| 生成 + 优化都做 | 画像 或 旧简历 | 灵活 | 两条路径，输入契约不统一，下游评估/导出要分支处理 |
| **只生成** | 画像 + Gap + 岗位 | 输入干净可控；画像已校验置信度，是可信事实源；定位清晰 | 用户不能"在原文上改" |

**最终选择**：只生成

**理由**：
- 画像由简历解析环节建立，带字段置信度，是结构化、可信的事实来源。从画像生成，输入确定、可控、可复现。
- "优化用户 PDF"会引入不可控变量：用户的原始简历质量、格式、信息密度差异巨大，"优化"的边界模糊（改到什么程度算优化？保留多少原文？），效果难以保证，也难以评估。
- 数据流因此更干净：用户上传的旧简历只是**画像的素材来源**（经 resume_parser 解析进画像），不是"待优化对象"。简历优化模块的输入契约统一为「画像 + Gap + 岗位」。
- 定位清晰，面试可讲：job-copilot 是"画像驱动的简历生成器"，不是"简历润色工具"——前者输入可控、产出可评估，是更工程化的选择。

**权衡**：放弃了"在我的原文上改"的用户心智。缓解：画像本身来自用户上传的简历（解析建立），所以"内容是用户的"，只是重新针对岗位组织与表述。

## 决策 3：质量保障 —— 6 维 LLM 评估 + 脚本格式校验（双层）

**选项对比**：

| 方案 | 内容评估 | 格式校验 | 优点 | 缺点 |
|------|----------|----------|------|------|
| 纯脚本 | ❌ | ✅ | 确定性、快 | 查不了语义（STAR 是否完整、表述是否空泛） |
| 纯 LLM | ✅ | 由 LLM 兼 | 语义强 | 格式硬规则交由 LLM 不可靠（占位符残留、模块顺序） |
| **双层** | ✅ LLM | ✅ 脚本 | 语义 + 确定性各司其职 | 两套实现 |

**最终选择**：双层（LLM 内容评估 + 脚本格式校验）

**理由**：
- 现有 `quality_checker.py` 只做**原始简历文本**的规则检测（长度/中文比例/乱码/结构关键词）和字段置信度计算，**没有针对"产出简历"的 LLM 内容评估**。这是本模块的最大质量增量。
- LLM 擅长语义判断（这条经历 STAR 完整吗？这个量化数字可信吗？表述空泛吗？），但不擅长确定性规则（占位符 `{{xxx}}` 是否残留、`# self-intro` 是不是首个 `#`、date 格式对不对）。脚本反之。双层结合覆盖两类问题。
- amlei-resume skill 正是双层结构：`resume-evaluator.md`（6 维 LLM 评估）+ `validate_resume.py`（格式硬校验）。本设计直接借鉴其成熟方案，降低设计风险。

**6 维评估维度与权重**（借鉴 skill 的 resume-evaluator，结合 job-copilot 画像驱动场景）：

| 维度 | 权重 | 核心检查 |
|------|------|----------|
| 基础规范 | 15% | 联系方式齐全、self-intro 完整、时间线无断层、排版、**脱敏**（无公司内部项目原名） |
| JD 匹配 | 25% | 关键词命中、能力对齐（技能重叠 ≥60%）、相关经历前置、隐性需求体现 |
| 成果量化 | 25% | STAR 完整性、至少 1 个可验证数字、强动词开头、无职责罗列 |
| 结构清晰 | 10% | 模块顺序合理、`#`/`##` 层级正确、无冗余重复、每段 3-5 条 bullet |
| 差异化 | 15% | 独特亮点、加分项（作品/开源/专利）、层级适配（初级重执行/高级重决策） |
| 语言表达 | 10% | 简洁无套话、客观基于事实、具体不抽象、主语明确（"我"非"我们"） |

**迭代规则**：每轮至少修复 1 个不通过项；所有维度"不通过"为 0 才算通过；超过最大轮次（默认 3）则带"仍需改进项"交付。

**格式校验硬规则**（借鉴 skill 的 validate_resume.py）：
- MD 校验：`# self-intro` 必须是首个 `#`；`name:` 必填；教育背景含毕业年份；只支持 `#`/`##` 层级；无空模块；`date:` 格式 `YYYY.MM — YYYY.MM|至今`
- HTML 校验：无残留 `{{占位符}}`；含 Header（姓名区）；含章节标题；含 `<style>`

**权衡**：两套实现。缓解：评估与校验都封装为独立 service，子图分别调用，互不耦合。

## 决策 4：Gap → 改写策略映射（兑现 JD 匹配的接口契约）

JD 匹配 design 决策 4 已定义 Gap 四分类与"下游简历优化如何消费"的映射。本模块**直接兑现**这个契约：

| Gap 类型 | 简历生成时的改写策略 |
|----------|---------------------|
| 硬技能差距（high） | 强化相关项目经历（把用到相邻/可迁移技能的项目前置并展开）+ 转移焦点（放大用户具备的相关能力） |
| 软技能表述弱（low） | STAR 改写（补情境/任务/行动/结果）+ 数据化（消灭"沟通能力强"式空泛） |
| 隐性偏好缺位（medium） | 挖掘可类比经历对冲（如无大厂背景 → 突出高复杂度/高影响力项目；无相关行业 → 突出可迁移方法论） |
| 红线预警（critical） | 策略性呈现 + 预警（不造假，但在简历中规避一票否决项的负面呈现；同时在评估报告中提示用户该项风险） |

**理由**：Gap 结构是两个模块的解耦点。定义清楚 Gap schema = 想清楚简历优化一半的输入。本模块只需把每类 Gap 翻译成生成 prompt 里的一条指令。

**实现**：生成 prompt 中，把 Gap 清单按类型分组，每组附对应的改写策略指令，LLM 据此组织简历内容与侧重。

## 决策 5：产出形态与 PDF 导出 —— L3（Markdown → HTML 主题 → A4 PDF）

**产出深度选项**：

| 档位 | 产出 | 优点 | 缺点 |
|------|------|------|------|
| L1 建议层 | 改写建议清单 | 实现最轻 | 不产出简历，不像一个"模块" |
| L2 草稿层 | Markdown 简历 + 评估迭代 | 闭环、工程量可控 | 无 PDF，投递不便 |
| **L3 导出层** | Markdown + HTML（主题）+ A4 PDF | 完整、可直接投递 | 工程量最大（主题系统 + PDF） |

**最终选择**：L3

**PDF 生成方式选项**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 前端浏览器打印 | 后端出 HTML，前端预览页 + 浏览器"打印为 PDF" | 零后端依赖；与 amlei-resume skill 路线一致；CSS 保真度高 | 用户需点"打印"；后端无 PDF 文件 |
| 后端 weasyprint | Python 原生 HTML→PDF | 后端直接产 PDF 文件 | Windows 装 GTK 依赖有坑；复杂分页 CSS 支持有限 |
| 后端 playwright（headless chromium） | 无头浏览器渲染→PDF | 保真度最高；可自动化检查页数/填充率 | 装 chromium 重（~数百 MB） |

**最终选择**：MVP 用**前端浏览器打印**（同 amlei-resume skill），后端渲染（weasyprint/playwright）作为可选增强。

**理由**：
- amlei-resume skill 的导出路线就是"装配 HTML → 套预览壳（A4 自动分页 + 导出 PDF 工具条）→ 浏览器打印"，并用 Playwright 做页数/填充率/行尾空白的自动化检查。这条路线零后端依赖、CSS 保真度高，已被验证。
- job-copilot 是 Windows 开发环境的个人作品集项目，引入 weasyprint（GTK 依赖）或 playwright（chromium）都有装配成本，不值得为 MVP 承担。
- 后端仍持久化 Markdown + HTML，PDF 由前端按需打印；后续若需"后端直接给 PDF 文件"（如批量、定时），再增量引入 weasyprint/playwright。

**主题系统**：MVP 先实现 1-2 套主题（借鉴 skill 的 `theme-tech-dense` 技术密集型 / `theme-soe-formal` 正式型），组件库从简（Header / SectionHead / Entry / Bullet 四类原子）。主题选择策略：岗位有明确契合则推荐，否则用默认主题。

**权衡**：MVP 不在后端产 PDF 文件。缓解：前端预览页带"导出 PDF"工具条，体验上是一键导出；HTML 已持久化，可随时补后端渲染。

## 决策 6：持久化 —— resumes 表，按岗位多份、按版本多次

**选项对比**：

| 方案 | 存储 | 优点 | 缺点 |
|------|------|------|------|
| 不持久化 | 仅内存返回 | 实现最轻 | 无法回看、无法换岗重定向、刷新即丢 |
| 单份覆盖 | 每用户存最新一份 | 简单 | 丢失历史、无法对比多岗位 |
| **多岗位多版本** | resumes 表，按 user+岗位+版本 | 支持历史回看、换岗重定向、迭代对比 | 表设计与查询稍复杂 |

**最终选择**：多岗位多版本（resumes 表）

**数据模型**（混合策略，标量拆列 + JSON，沿用既有 user_profiles / jd_match_results 风格）：

```
resumes
  id            UUID PK
  user_id       FK→users
  target_position  目标岗位（标量）
  jd_result_id  FK→jd_match_results（可空，关联的匹配结果）
  version       版本号（同 user+岗位 内自增）
  status        draft / refining / finalized
  theme         使用的主题
  content_md    Markdown 简历全文（TEXT）
  html          渲染后的 HTML（TEXT，可空——导出后填）
  eval_report_json  6 维评估报告（JSON）
  eval_score    综合评估分（标量，便于排序）
  created_at / updated_at
```

**路径 A 与 B 的持久化语义**：
- 路径 A：自动生成完成 → 写入一条 `status=draft, version=1`。用户接受即结束；用户进入精修则转 B。
- 路径 B：精修会话的中间态（当前草稿、评估、反馈历史、轮次）由 **checkpointer** 保存（thread_id = resume 会话），不每次落 DB。每次用户"满意导出"或每隔 N 轮，写入一条新版本（`version=n, status=finalized`）。DB 只存"确认的版本"，避免中间态污染。

**理由**：
- 一份画像针对多个岗位生成多份简历（换岗重定向）是核心场景，必须按岗位维度存储。
- 路径 B 的多轮迭代天然产生版本，按版本存储支持"对比这一版改了什么"。
- 中间态走 checkpointer、确认态走 DB，是 mock-interview 已验证的范式（会话态 vs 持久态分离）。

**权衡**：表与查询稍复杂。缓解：沿用既有混合模型范式，profile_service 的 upsert/读写模式可直接参考。

## 决策 7：与既有能力的集成（接口契约兑现）

### 消费 JD 匹配的 Gap（承上）
```
jd_match_results.gaps_json  ──▶  简历优化的输入
每个 gap = { type, requirement, current_state, suggestion, severity }
```
本模块启动时从关联的 `jd_match_result` 读取 Gap 清单作为快照（同 mock-interview 的 profile_snapshot 思路，保证生成过程中 Gap 不变），按决策 4 映射为改写策略。

### 复用模拟面试的 interrupt / checkpointer（B 模式同构）
路径 B 的精修会话跨多次请求，复用 mock-interview 的 checkpointer（见 `graph/checkpointer.py`）保存会话状态，用 interrupt 机制在"等用户反馈"处暂停。thread_id = resume 会话 ID。

### router 接入
`state.py` 已定义 `intent = "resume_optimize"`，但 `graph.py` 的 `_route_intent` 没有对应分支。本变更补齐：router 识别 `resume_optimize` → 进入简历优化子图入口。

### 画像读取
沿用 `profile_service.get_profile`，读取当前用户画像。画像缺失 → 中止并引导（同 JD 匹配的 profile_missing 处理）。

## 关键流程图

### 路径 A（自动迭代流水线）
```
[画像 + Gap + 岗位] → [就绪性检查] ─画像/Gap缺失→ END(引导)
                          │ 就绪
                          ▼
                    [生成 Markdown 草稿] ◀──────────┐
                          │                        │
                          ▼                        │ 反馈
                    [6 维 LLM 评估]                │
                          │                        │
                   ┌──────┴──────┐                 │
                不通过(≤N轮)    通过               │
                   │             │                 │
                   └─────────────┴─────────────────┘
                          │ 通过或达上限
                          ▼
                    [格式硬校验] ─ERROR→ 修复重装
                          │
                          ▼
              [装配 HTML（主题）→ 预览壳]
                          │
                          ▼
                [持久化 status=draft, v1]
                          │
                          ▼
            返回用户：HTML/PDF + 评估报告 + resume_id
                          │
                  resume_refine_offered = True
```

### 路径 B（人机协同精修）
```
用户触发精修（带 resume_id + 反馈）
        │
        ▼
  [resume_mode = refine]
        │
        ▼
  [按反馈改写草稿]（或画像追问挖亮点 → 补画像 → 改写）
        │
        ▼
  [6 维 LLM 评估]
        │
        ▼
  ╔═══════ interrupt ═══════════╗
  ║ 前端：草稿 + 评估 + 反馈入口 ║
  ╚═════════════════════════════╝
        │
   ┌────┴────┐
 反馈再改   "满意"
   │         │
   └─▶ 回改写  ▼
        [格式校验 → 导出 PDF → 持久化 status=finalized, v_n]
                    │
                    ▼
                返回定稿 PDF
        （跨请求；checkpointer 保存会话中间态）
```

## 边界与降级

- **画像缺失**：中止生成，返回 `PROFILE_MISSING` 引导先建画像（同 JD 匹配）。
- **Gap 缺失**（未关联匹配结果或匹配无 Gap）：降级为"通用简历生成"（仅基于画像，不针对特定 Gap），并提示用户"未检测到岗位差距，已生成通用版本，建议先做 JD 匹配"。
- **LLM 生成失败**：指数退避重试，耗尽返回友好错误，保留已输入信息。
