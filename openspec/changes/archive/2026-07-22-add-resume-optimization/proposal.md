# Proposal: 简历优化（画像驱动的简历生成与定制）

## Why（为什么需要）

### 当前痛点
JD 匹配分析让用户看清了「我差在哪」，但下一步「简历具体该怎么写」仍然是断的：用户拿到一份 Gap 清单（"缺 Kafka 经验""软技能表述空泛""需要数据化"），却要把这些建议**手动翻译成简历文字**——多数人翻译不动，于是 Gap 分析的价值止步于诊断。

市面上的简历工具分两类，都不解决这个问题：
- **润色类**：要求用户先有一份简历，在原文上改——但用户的原始简历质量参差、格式各异，优化空间和效果都不可控。
- **模板填空类**：给个空模板让用户填——填出来的还是用户自己写不出来的那些话，没有"针对这个 JD 帮我想想该写什么"的能力。

### 产品价值
**简历优化**是求职 Copilot 全链路的**兑现环节**——把前三环（画像、JD 匹配、Gap 分析）的积累，兑现成一份**可直接投递的简历**：

1. **承上**：消费画像（用户有什么）+ Gap 清单（岗位要什么、差在哪），让前三环的产出产生闭环价值
2. **兑现承诺**：JD 匹配的 design 明确把 Gap 结构定义为"简历优化的输入契约"——本变更把这个契约兑现，闭合全链路（建立画像 → JD 匹配 → 简历生成 → 模拟面试）
3. **差异化定位**：**画像驱动的生成器**，而非润色工具——输入永远是「结构化画像 + Gap」两个确定的东西，不引入"用户简历质量参差"的不可控变量；输出是针对目标岗位定制的全新简历，而非在原文上贴补丁
4. **教育价值**：在生成与精修过程中，用户看到"一个好的项目经历应该怎么写"，沉淀为可复用的写简历能力（对齐产品方案"求职教练"定位）

### 战略定位
简历优化把产品从"诊断工具"推向"产出工具"。诊断告诉用户"差在哪"，产出帮用户"写出来"——后者才是用户最终投递需要的东西。它和模拟面试一起，构成"从分析到行动"的闭环后半段。

## What Changes（做什么变更）

### 新增能力
1. **resume-optimization（简历优化）**
   - **画像与差距驱动的简历生成**：基于用户画像 + 目标 JD 的 Gap 清单，从零生成针对该岗位的定制简历（只生成，不接收旧简历作为优化底稿）
   - **双层质量门**：6 维 LLM 内容评估（基础规范 / JD 匹配 / 成果量化 / 结构清晰 / 差异化 / 语言表达）+ 脚本化格式校验（self-intro 首模块、必填字段、标题层级、占位符残留等硬规则）
   - **A+B 混合交互**：路径 A 默认自动迭代流水线（生成 → 评估 → 自动改写迭代 → 导出），路径 B 可选人机协同精修（interrupt、反馈改写、画像追问、满意定稿）
   - **L3 完整产出**：Markdown 简历 → HTML（主题渲染）→ A4 PDF
   - **简历持久化**：按岗位多份、按版本多次，支持历史回看与换岗重定向

### 系统变更
- **LangGraph 状态机扩展**：新增简历优化子图
  - 路径 A 与简历解析 / JD 匹配**同构**（输入校验 → 生成 → 质量门 → 迭代 → 格式化产出）
  - 路径 B 与模拟面试**同构**（interrupt + checkpointer 长程会话）
- **State 扩展**：新增 `ResumeOptimizeState`（目标岗位、Gap 快照、画像快照、简历草稿、评估报告、迭代轮次、导出产物、模式与 interrupt 控制等字段）
- **router 扩展**：`resume_optimize` 意图新增分发分支（已有意图名，补节点与边）
- **API 新增**：
  - `POST /api/resume/generate`（路径 A：画像 + Gap + 岗位 → 自动生成 → 返回 PDF + 评估 + resume_id）
  - `POST /api/resume/{id}/refine`（路径 B：用户反馈 → 改写 → 返回新草稿 + 评估，interrupt 语义）
  - `POST /api/resume/{id}/finalize`（路径 B：满意 → 导出定稿 PDF → 落库 finalized）
  - `GET /api/resume/list`（按用户查简历列表，按岗位分组）
  - `GET /api/resume/{id}`（单份详情，含指定版本）
  - `GET /api/resume/{id}/pdf`（下载 PDF）
- **数据层新增**：
  - `resumes` 表（简历持久化：按用户 + 岗位 + 版本维度）
- **前端组件新增**：
  - `ResumeOptimizer.vue`（简历生成主页面：触发生成、查看 PDF、进入精修）
  - `ResumePreview.vue`（简历 PDF / HTML 预览）
  - `ResumeEvalReport.vue`（6 维评估报告展示）
  - `ResumeRefine.vue`（路径 B 精修交互：反馈输入 + 迭代轮次 + 满意定稿）
  - `ResumeHistory.vue`（简历历史，按岗位分组、按版本回看）

## Capabilities（能力清单）

### resume-optimization（简历优化）
**能力描述**：将用户个人画像与目标 JD 的差距分析（Gap）作为输入，从零生成一份针对该岗位的定制简历，经双层质量门（LLM 评估 + 格式校验）迭代打磨，产出 Markdown / HTML / A4 PDF 三种形态，支持自动生成与人机协同精修两种模式。

**核心流程（路径 A 自动）**：
```
画像 + Gap 清单 + 目标岗位
   → 就绪性检查（画像是否可用）
   → 生成 Markdown 草稿（Gap→改写策略 + STAR/脱敏/平实规则）
   → 6 维 LLM 评估
   → 不通过则带反馈自动迭代（≤ N 轮）
   → 格式硬校验
   → 装配 HTML（主题）→ 导出 A4 PDF
   → 持久化（status=draft）→ 返回用户
```

**核心流程（路径 B 精修，可选）**：
```
用户在 A 产出基础上触发精修
   → interrupt：展示当前草稿 + 评估 + 反馈入口
   → 用户反馈 / 画像追问挖亮点 → 改写 → 重新评估
   → 循环（跨请求，checkpointer 保存会话）
   → 用户"满意" → 校验 → 导出定稿 PDF → 持久化（status=finalized）
```

**Gap → 改写策略映射**（接续 JD 匹配 design 决策 4）：
- 硬技能差距 → 强化相关项目经历 + 转移焦点（放大相邻可迁移技能）
- 软技能表述弱 → STAR 改写 + 数据化
- 隐性偏好缺位 → 挖掘可类比经历对冲（如无大厂背景 → 突出高复杂度/高影响力项目）
- 红线预警 → 策略性呈现 + 预警（不造假，规避一票否决）

**6 维评估维度**（权重）：基础规范（15%）/ JD 匹配（25%）/ 成果量化（25%）/ 结构清晰（10%）/ 差异化（15%）/ 语言表达（10%）

## Impact（影响分析）

### 用户体验影响
**正面影响**：
- Gap 分析的建议真正落地成简历文字，从"知道差在哪"到"看到怎么写"
- 默认自动出活（路径 A），几十秒拿到一份可投递的 PDF
- 想精修的用户可进入路径 B，全程掌控、顺带学习简历写法
- 一份画像可针对多个岗位生成多份简历，支持换岗重定向

**潜在风险**：
- LLM 生成内容可能失真或编造 → 缓解：评估层的"成果量化可信度"维度把关 + 生成 prompt 约束"不替用户编造，缺素材时标注待补"
- 画像不足导致生成空洞 → 缓解：路径 B 的画像追问机制 + 就绪性检查提示"画像不完整"
- PDF 排版分页不理想 → 缓解：导出环节的页数/填充率检查 + 主题适配

### 技术影响
**依赖复用**：复用已有的 LLM 配置、结构化输出（`get_structured_llm`）、重试机制（`invoke_llm_with_retry`）、置信度计算、SQLAlchemy 基建；路径 B 复用模拟面试已建好的 checkpointer + interrupt 机制。无新核心依赖。

**性能影响**：
- 路径 A：生成 + 评估 + 迭代（1-3 轮）+ 导出，端到端预计 30-60 秒
- 路径 B：每轮精修约 10-20 秒，轮数由用户决定
- MVP 采用同步 API + 前端分阶段进度提示（沿用简历解析 / JD 匹配模式）

**架构影响**：
- LangGraph 新增一个**双范式**子图：路径 A 同构 jd_match（流水线），路径 B 同构 mock-interview（interrupt 长程会话）
- 引入 `resumes` 持久化表，数据模型采用混合策略（标量拆列 + 不定长 JSON，沿用既有风格）
- 兑现 JD 匹配 design 的"Gap → 简历优化"闭环接口契约

### 开发影响
**工作量估算**：
- 后端 - 路径 A 核心（数据层 + 生成服务 + 评估服务 + 格式校验 + 子图 + API）：8-10 天
- 后端 - 导出（主题系统 + HTML 装配 + PDF）：3-4 天
- 后端 - 路径 B 精修（interrupt + checkpointer 集成 + refine/finalize API）：3-4 天
- 前端：4-5 天（生成页、预览、评估报告、精修交互、历史）
- Prompt 调优：2-3 天（生成 prompt、6 维评估 prompt、Gap→改写映射）
- 测试与打磨：2 天
- **总计：约 22-28 天**（路径 A 可先行交付，路径 B 作为增量）

**技术风险**：
- 生成简历的事实准确性 → 缓解：评估层把关 + prompt 约束 + 画像作为唯一事实来源
- 6 维评估主观性与稳定性 → 缓解：结构化输出约束 + 阈值可配置 + 样本调优
- PDF 排版与中文字体 → 缓解：MVP 先用浏览器打印（零依赖，同 amlei-resume skill 路线），后端渲染作为可选增强
- 主题装配复杂度 → 缓解：MVP 先实现 1-2 套主题，组件库从简

## Success Criteria（成功标准）

### 功能验收
- [ ] 能基于画像 + Gap + 岗位自动生成一份结构完整的 Markdown 简历
- [ ] 路径 A 全流程跑通：生成 → 评估 → 迭代 → 校验 → 导出 PDF → 落库
- [ ] 6 维评估能输出各维度得分、通过项与不通过项、优先级改进列表
- [ ] 格式校验能拦截硬错误（self-intro 首模块缺失、占位符残留、date 格式错误等）
- [ ] 路径 B 能 interrupt、接收反馈改写、画像追问、满意定稿
- [ ] 简历按岗位多份、按版本多次持久化，可查历史与下载 PDF
- [ ] 画像缺失 / Gap 缺失时给出明确引导

### 质量验收
- [ ] 生成的简历内容忠实于画像（不编造经历），量化数字合理可解释
- [ ] Gap 的四类改写策略在简历中有体现（可追溯）
- [ ] 6 维评估稳定（同输入多次评估结果一致为主）
- [ ] LLM 失败有重试与友好降级
- [ ] PDF 排版符合 A4，页数与填充率合理

### 用户体验验收
- [ ] 用户在 JD 匹配报告后能一键"生成简历"
- [ ] 路径 A 在 1 分钟内拿到可预览的 PDF
- [ ] 评估报告清晰指出"哪好、哪要改、优先改什么"
- [ ] 路径 B 的反馈交互顺畅，能看到简历逐轮变好
