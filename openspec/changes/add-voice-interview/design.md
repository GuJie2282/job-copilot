# Design: 模拟面试语音回答（add-voice-interview）

## 设计原则

1. **零侵入核心链路**：语音是输入层的增强，不是新业务。识别结果以文本接入现有 `submitAnswer`，LangGraph 面试子图、checkpointer、评估/追问/复盘一律不动。后端不感知回答来源——这保证语音功能挂掉时文字面试完全不受影响。
2. **沉浸优先、纠错兜底**：默认不显示识别文字（避免自我审查破坏口语自然度），但保留长按回看（识别错了能发现）。沉浸与纠错用"默认隐藏 + 主动展开"平衡，而非二选一。
3. **收音耦合状态机**：收音的开关跟随面试对话状态（面试官说话时关、轮到用户时开），不是孤立的 UI 控件。让收音成为 LangGraph 状态机在前端的镜像，而非用户要操心的额外动作。
4. **数据自持**：语音识别本地部署（faster-whisper），音频/文本不出服务器。与项目 RAG 不用云向量库、面经库数据私有是同一个调性。
5. **诚实的技术判断**：ASR 引擎、识别模式、录音格式等选型都以"能跑起来、能讲清道理"为准，先 de-risk 再铺开；新技术（ASR、MediaRecorder）只用在真正提升沉浸感的地方。

---

## 核心设计决策

### 决策 1：ASR 引擎选型——faster-whisper 本地部署

**选项对比**：

| 选项 | License | 免费 | 中文质量 | 离线 | 致命问题 | 选择 |
|------|---------|------|---------|------|----------|------|
| Web Speech API（浏览器原生） | 标准 | ✅ | Chrome 极好 | ❌ Chrome 需联网 | Chrome 底层=发 Google 服务器识别，国内不可控；数据出境；兼容性差（Firefox 几乎不可用）；拿不到音频 | ❌ |
| Whisper Web（transformers.js，前端 WASM） | MIT | ✅ | base 一般/small 好 | ✅ | 模型 145-488MB 首次加载慢；WASM 推理慢；中文 base 错字多 | ❌ |
| Vosk-browser（前端 WASM） | Apache 2.0 | ✅ | 中等 | ✅ | 面试专业术语弱（A/B、DAU 易错）；仍要下载模型 | ❌ |
| **后端 faster-whisper** ⭐ | **MIT** | ✅ | **small+ 很好** | ✅ | 需验证 Windows 安装 + 模型下载 | ✅ |
| 后端 Vosk（Python） | Apache 2.0 | ✅ | 中等 | ✅ | 中文质量弱于 Whisper | ❌ |
| 国内云 ASR（智谱/讯飞/阿里/百度） | 商用 | ⚠️ 限额 | 极好 | ❌ | 免费额度有限；数据出境第三方；违背"数据自持"基调 | ❌ |

**最终选择**：后端 faster-whisper（small 模型）

**理由**：同时满足"免费 + 无侵权 + 质量好"三项硬约束，且最契合项目调性：
- **MIT 开源、完全免费、无侵权**：Whisper 是 OpenAI 开源、faster-whisper 是 CTranslate2 量化加速版，双 MIT
- **中文质量业界标杆**：small 级别对面试专业术语识别强
- **数据不出服务器**：呼应项目"数据自持"哲学（与 RAG 不用云向量库同调性）
- **复用后端基建**：已有 python-multipart + resume.py 的 UploadFile 范式，加一个端点即可

**权衡**：需要后端算力与首次模型下载。缓解：阶段 1 先做最小 spike 验证 Windows 安装与延迟（de-risk）；CPU 跑 small 一段录音预计 3-8s，可接受。

**备选方案（spike 失败时降级）**：若 faster-whisper 在 Windows 装不上 → 降级后端 Vosk（Apache 2.0，质量略低但稳）→ 再不行降级 Whisper Web 前端（牺牲首次加载体验换可用性）。降级链路在设计阶段就明确，避免实现期卡死。

---

### 决策 2：识别位置——后端，而非前端 WASM

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 前端 WASM（Whisper Web / Vosk-browser） | 数据不出浏览器（隐私极佳）、离线、无后端负担 | 模型大（首次下载几百 MB）、WASM 推理慢、中文质量打折 | ❌ |
| **后端 faster-whisper** ⭐ | 质量最好、复用上传基建、数据自持、模型只装一次 | 占后端 CPU/内存、音频要上传 | ✅ |

**最终选择**：后端识别

**理由**：
- 项目是个人演示作品集，单用户场景，后端 CPU 跑 ASR 完全够；前端 WASM 的"隐私"优势在"数据本来就在自己服务器"的前提下不增益
- 后端复用现有 multipart 上传基建（resume.py 范式），集成成本最低
- 模型只在后端装一次，前端零下载——首次进入面试间体验远优于前端 WASM
- 数据自持：音频上传到自己的后端转写即弃，不出服务器

**权衡**：音频要上传（增加一次网络传输）。但面试回答录音本就不大（15-30s 语音约几百 KB），上传开销可忽略。

---

### 决策 3：识别模式——批处理（录完再识别），不做流式

**选项对比**：

| 选项 | 触发结束 | 引擎契合度 | 复杂度 | 选择 |
|------|----------|-----------|--------|------|
| **批处理（录完再识别）** ⭐ | 用户手动结束 | faster-whisper 天然适合（批处理设计） | 低 | ✅ |
| 流式（边说边识别） | VAD 静默自动断句 | faster-whisper 不擅长，需专门流式引擎 | 高（WebSocket + VAD） | ❌ |

**最终选择**：批处理模式

**理由**：产品需求明确"支持用户暂停、结束"——**既然要手动结束，就天然落在批处理**。这是个意外的好处：
- faster-whisper 就是为批处理设计的，质量最好、实现最简单
- 不需要 WebSocket、不需要 VAD 静默检测、不需要流式分片
- 识别有完整上下文，专业术语识别更准
- 与"不显示文字"的沉浸诉求一致（流式的"边说边出字"在沉浸模式下优势用不上）

**权衡**：用户说完才识别，期间有几秒"识别中"等待。但这是手动结束的预期内开销，状态栏明确提示即可管理预期。

**讲点**：若当初选"自动静默断句"（说完自动提交），会被逼到流式模式，复杂度翻倍。"手动结束"决策顺便避开了最难的坑——这是产品决策与技术复杂度联动的典型案例。

---

### 决策 4：零侵入架构——语音是输入层增强 ⭐

**最终选择**：语音识别结果以文本形式接入现有 `submitAnswer`，整个 Agent 链路不动。

```
[文字模式]                              [语音模式]
  用户打字                                 用户说话
    │                                       │
    ▼                                  MediaRecorder 录音
  answer(text)                              │ 手动结束
    │                                       ▼
    │                              POST /api/interview/voice/transcribe (唯一新增)
    │                                       │ faster-whisper 转写
    │                                       ▼
    └─────────────► answer(text) ◄──────────┘
                       │
                       ▼
              submitAnswer(sessionId, text)   ← 两条路汇合，完全复用
                       │
                       ▼
           POST /api/interview/sessions/:id/answer
                       │
                       ▼
              LangGraph 面试子图（零改动）
              checkpointer / evaluator / 追问 / 复盘（零改动）
```

**理由**：语音识别本质是"把打字换成说"——对 Agent 而言，回答依旧是 `answer: string` 文本。后端不需要、也不应该知道回答来源。这意味着：
- **后端只新增 1 个转写端点**（接音频、返文本）
- **submitAnswer 与整个 LangGraph 链路、checkpointer、评估/追问/复盘完全不动**
- **语音功能挂掉（模型没装上/识别失败）不影响文字面试**——纯增量增强，风险隔离

**权衡**：后端 transcript 里 answer 只有文本，丢失了"这段是语音来的"信息。但本就不需要——语音条是前端实时交互的呈现，transcript 存文本足够支撑复盘与面经沉淀。

**讲点**：这是架构解耦的范例。输入方式的切换（文字→语音）没有污染核心 Agent，因为 Agent 的契约本就是"接收文本回答"。好的架构让扩展是增量的、可回退的。

---

### 决策 5：全自动状态机收音——收音跟随面试状态

**最终选择**：收音的开关由面试对话状态机自动控制，而非用户手动。

```
面试间状态                   收音      底部指引
─────────────────────────────────────────────────────────
面试官提问/思考(submitting)   OFF       "面试官正在准备问题…"
        │ currentQuestion 就绪
        ▼
轮到用户回答                  ON(自动)  "🎤 轮到你了，开始回答吧"
        │
        ▼
聆听中                        ON        "🎙 正在聆听 0:18  [暂停][说完了]"
        ├── 暂停 → 已暂停     OFF       "⏸ 已暂停  [继续][说完了]"
        │     └ 继续 → 回聆听中
        ▼ 手动结束
识别中                        OFF       "正在识别你的回答…"
        │ faster-whisper 返回文本
        ▼
提交+评估(submitting)         OFF       "面试官正在评估你的回答…"（复用现有）
        │
        ▼ 追问 / 下一题 → 回到顶部
```

**理由**：面试间本来就是状态驱动的（`loading` → 有题待答 → `submitting` → 出下一题）。让收音跟随这个状态机，而非引入用户要操心的"开始录音/停止录音"控件——这才是"像真面试"（真人面试不用按按钮开始录音）。收音成为 LangGraph 状态机在前端的镜像，是 Agent 思维的延伸。

**权衡**：自动收音会录进环境噪音与停顿。缓解：① 用户可主动"暂停"避噪思考；② Whisper 有一定抗噪能力，能处理"嗯啊"口癖；③ 当前面试官问题是文字气泡（无 TTS 播放），不存在"面试官声音被回授收进去"的问题。

---

### 决策 6：录音控件——录音机式（自动开始/暂停/继续/手动结束）

**选项对比**：

| 选项 | 交互 | 适合 | 选择 |
|------|------|------|------|
| 微信按住式 | 按住说话、松开发送、上滑取消 | 移动端、短消息 | ❌ |
| **录音机式** ⭐ | 自动开始、暂停、继续、手动结束 | 桌面端、长回答、需思考停顿 | ✅ |

**最终选择**：录音机式 + 状态机自动触发

**理由**：
- 面试回答是长段落（15-60s），需要思考停顿，按住式不适合（一直按着累、松手就发送）
- "暂停"功能（用户决策完整版）让用户卡壳时能主动避噪思考，说好了"继续"——这是录音机式的天然能力
- 结合决策 5 的状态机自动开始，用户连"开始"都不用按：轮到你就自动开录，说完点"结束"即可

**权衡**：录音机式需用户主动点"结束"（不像按住式松手即发）。但这恰好契合决策 3 的批处理模式（手动结束触发识别），且给用户"说完了"的掌控感。

---

### 决策 7：静默不自动断——保留思考空间（用户决策 1a）

**最终选择**：用户开启收音后，不因静默自动结束录音，一直录到用户手动点"结束"。

**理由**：面试中正常思考停顿（组织语言、回忆细节）可能持续数秒甚至更久，自动断句会打断思路、误提交半句话。保留充分思考空间更贴近真实面试节奏。用户有"暂停"按钮主动避噪，不需要系统替他判断"说完了"。

**权衡**：用户走神/离开时录音会一直进行，可能录进长段无效音频。缓解：① 录音时长有上限保护（如单段最长 5 分钟，超时自动结束并提示）；② Whisper 能处理静默段（不会因此报错）。不引入 VAD 静默检测，保持简单。

---

### 决策 8：沉浸与回看——默认不显示文字，长按可回看（用户决策 2）

**最终选择**：消息流中用户回答以"语音条"呈现（不显示识别文字），长按/点击语音条可展开识别文字（仅自己纠错）。

```
默认（沉浸）                      长按/点击（回看）
┌─────────────┐                  ┌─────────────┐
│ ▶ 0:18 ▏▏▏▏ │  ← 语音条        │ ▶ 0:18 ▏▏▏▏ │
└─────────────┘                  │─────────────│
                                  │ "我在字节做  │ ← 识别文字展开
                                  │  feed 推荐…"│   （仅自己看，不进消息流）
                                  └─────────────┘
```

**理由**：两个诉求冲突，用"默认 + 主动"而非二选一：
- **沉浸**：默认不显示文字，避免用户看着识别结果自我审查、破坏口语自然度（这是语音模式的初衷）
- **纠错**：识别非 100% 准确（专业术语、口音），完全不回看则用户无法发现识别错误影响后续答题。长按展开让纠错可选、不打断

**权衡**：长按回看增加一点交互复杂度。但比"全程显示文字（破坏沉浸）"和"完全不可见（无法纠错）"两个极端都好——这是产品判断的精细度。

**关键区分**：
- ❌ 全程显示识别文字 → 诱导自我审查，违背语音模式初衷
- ❌ 完全不可见 → 识别错了无法发现，影响后续
- ✅ 默认隐藏 + 主动展开 → 沉浸优先，纠错兜底

---

### 决策 9：降级链路——权限/设备/识别失败均降级文字

**最终选择**：任何语音链路失败都降级回文字输入，不阻断面试。

| 失败场景 | 降级动作 | 提示 |
|----------|----------|------|
| 麦克风权限拒绝 | 切文字模式 + toast | "未获得麦克风权限，已切换文字输入" |
| 设备不支持麦克风/无输入设备 | 切文字模式 + toast | "未检测到麦克风，已切换文字输入" |
| 浏览器不支持 MediaRecorder | 切文字模式 + toast | "当前浏览器不支持语音输入，已切换文字" |
| 识别失败（后端转写报错） | 语音条标红 + 重试/切文字 | "识别失败，点此重试或切换文字" |
| 识别结果为空（录音太短/无声） | 语音条标红 + 重新录制 | "未识别到内容，请重新回答" |

**理由**：语音是增强体验，不是核心能力。任何环节失败都应有兜底，保证面试能继续。与项目现有"LLM 失败降级""检索失败降级"哲学一致。

---

### 决策 10：录音格式与解码——优先直读 webm，降级转码

**最终选择**：浏览器 MediaRecorder 默认录 `audio/webm;codecs=opus`，优先让 faster-whisper 经 PyAV 直读；PyAV 不可用则用 pydub + ffmpeg 转 wav。

**理由**：
- MediaRecorder 各浏览器默认格式不一（Chrome/Firefox: webm/opus；Safari: mp4），webm 是最普遍的
- faster-whisper 内部用 PyAV（av 库）解码，原生支持 webm/opus——理论可零转码
- 若 PyAV 在 Windows 装不上（av 依赖也较重），降级 pydub（需系统装 ffmpeg.exe）转 wav

**权衡**：理想是零转码直读，但 PyAV/ffmpeg 在 Windows 的可用性需 spike 验证。这是阶段 1 de-risk 的重点之一。

### 语音回答时序图（一轮完整生命周期）

```
① 面试官提问完成（currentQuestion 就绪）
   前端: 收音 OFF → ON（自动开启）+ 指引"🎤 轮到你了"
         MediaRecorder.start()

② 用户开口回答
   前端: 指引"🎙 正在聆听 0:18  [暂停][说完了]"
         （用户可暂停/继续避噪思考）

③ 用户点"说完了"
   前端: MediaRecorder.stop() → Blob(webm)
         收音 ON → OFF + 指引"正在识别你的回答…"
         语音条入消息流（叠加转圈）

④ 上传转写
   前端 ──POST multipart──▶ 后端 /voice/transcribe
   后端: faster-whisper 转写 → 文本
   后端 ──{text}──▶ 前端

⑤ 文本接入答题链路（与文字模式汇合）
   前端: 语音条转圈停止（识别完成）
         指引"面试官正在评估你的回答…"
   前端 ──POST answer{text}──▶ 后端 /sessions/:id/answer
   后端: LangGraph evaluator 评估 + 决策
         ├─ 追问/下一题 → 返回下一题
         └─ 结束 → 返回 finished

⑥ 下一题渲染（currentQuestion 就绪）
   前端: 回到步骤 ①（收音自动开启）
```

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| faster-whisper Windows 安装失败（CTranslate2 wheel） | 阻塞后端 | 中 | 阶段1 最小 spike 先验证；失败降级 Vosk 后端 / Whisper Web 前端 |
| HuggingFace 模型下载慢/失败（国内网络） | 首次启动卡住 | 中 | HF 镜像（HF_ENDPOINT=hf-mirror.com）或预置模型文件 |
| 录音格式 webm 解码失败（PyAV 不可用） | 转写报错 | 中 | spike 验证直读；不行降级 pydub+ffmpeg 转 wav |
| CPU 推理延迟过长 | 体验下降 | 中 | 实测 small 延迟；过慢降级 tiny/base 或提示用户 |
| 识别准确率不达预期（专业术语/口音） | 影响后续答题 | 中 | 可回看识别文字；识别失败可重试/切文字；Prompt 评估对口语化回答容错 |
| 自动收音误收环境音/键盘声 | 识别噪声 | 低 | 用户可暂停避噪；Whisper 抗噪；面试官问题无 TTS 不回授 |
| 麦克风权限/设备问题 | 语音不可用 | 中 | 全链路降级文字模式 + 清晰提示 |
| 浏览器兼容性（MediaRecorder/Safari） | 部分浏览器不可用 | 中 | 降级文字；演示用 Chrome/Edge |

## 技术选型总结

| 层级 | 选择 | 理由 |
|------|------|------|
| ASR 引擎 | faster-whisper（small） | MIT 免费、中文质量好、本地部署数据自持 |
| 识别位置 | 后端 | 复用上传基建、模型只装一次、质量最好 |
| 识别模式 | 批处理（录完再识别） | 手动结束天然契合、faster-whisper 设计模式、无需 VAD |
| 架构 | 零侵入（输入层增强） | 后端只加1端点、Agent 链路不动、风险隔离 |
| 收音控制 | 状态机自动（跟随面试状态） | 像真面试、Agent 思维延伸 |
| 录音控件 | 录音机式（自动/暂停/继续/结束） | 适合长回答与思考停顿 |
| 静默策略 | 不自动断 | 保留思考空间 |
| 呈现 | 语音条 + 长按回看 | 沉浸优先、纠错兜底 |
| 降级 | 全链路文字兜底 | 语音是增强，不阻断面试 |
| 录音格式 | webm 直读，降级转 wav | 零转码优先，可用性兜底 |

## 面试讲解要点

1. **为什么不用浏览器原生 Web Speech API？**
   - Chrome 底层把音频发到 Google 服务器识别，国内不可控、数据出境
   - 兼容性差（Firefox 几乎不可用）、拿不到音频本身
   - 选 Whisper 本地部署：免费、合规、可控、数据不出服务器

2. **为什么选 faster-whisper 而非云端 ASR？**
   - 云端免费额度有限、数据出境第三方，违背项目"数据自持"基调
   - 这和项目 RAG 不用云向量库、面经库数据私有是同一个产品哲学——数据自持是壁垒

3. **为什么是"批处理"而非"流式实时识别"？**
   - 产品需求要"手动结束"，天然落在批处理——产品决策与技术复杂度联动
   - 流式需 WebSocket + VAD 静默检测，复杂度翻倍，且与"不显示文字"的沉浸诉求冲突
   - "手动结束"决策顺便避开了最难的坑——这是产品判断驱动技术取舍的范例

4. **架构为什么是零侵入？**
   - 语音识别本质是"把打字换成说"，对 Agent 而言回答依旧是文本
   - 后端只加 1 个转写端点，整个 LangGraph 面试链路、checkpointer、评估/追问/复盘不动
   - 语音挂掉不影响文字面试——好的架构让扩展是增量的、可回退的

5. **收音为什么做成"全自动状态机"而非"按按钮录音"？**
   - 面试间本来就是状态机驱动的，让收音跟随状态（面试官说话时关、轮到用户时开）
   - 真人面试不用按按钮开始录音——收音是状态机的镜像，是 Agent 思维的延伸

6. **沉浸与纠错怎么平衡？**
   - 默认不显示识别文字（避免自我审查破坏口语自然度）
   - 长按可回看（识别错了能发现）
   - 用"默认隐藏 + 主动展开"而非二选一——产品判断的精细度

7. **降级链路体现了什么？**
   - 语音是增强体验不是核心能力，任何失败都降级文字、不阻断面试
   - 与项目"LLM 失败降级""检索失败降级"一脉相承的工程哲学
