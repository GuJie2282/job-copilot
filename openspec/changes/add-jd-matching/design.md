# Design: JD 匹配分析

## 设计原则

1. **可解释优先**：用户要的不是"75 分"这个数字，而是"为什么 75、差在哪、怎么补"。每个得分点都要有出处。
2. **承上启下**：JD 匹配是闭环枢纽——消费上游画像，产出 Gap 喂给下游简历优化。Gap 的结构就是两个模块的接口契约。
3. **同构复用**：沿用简历解析的子图范式（输入校验 → 质量门 → 结构化提取 → 计算 → 格式化），降低认知与维护成本。
4. **混合而非堆料**：程序化比对做确定性的硬技能匹配，LLM 只判规则搞不定的隐性偏好——各司其职，稳定且可解释。

---

## 核心设计决策

### 决策 1：匹配算法选型

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 纯 LLM 整体打分（JD+画像全塞给 LLM） | 最快、最简单 | 黑盒、不稳定、无法解释"凭什么 75 分" | 不选 |
| 混合式（结构化 + 程序比对 + LLM 判隐性 + 加权） | 可解释、可追溯、稳定 | 多几步、需设计权重 | ✅ 选择 |
| 向量 embedding 语义匹配 | 语义准、技术深 | 可解释性差（"相似度高但说不清为啥"）、MVP 偏重 | P2 增强 |

**最终选择**：混合式

**理由**：匹配度的核心矛盾是**可解释性**。把匹配拆成三件事——JD 结构化（像简历一样）、逐项可追溯比对、LLM 只负责规则判不了的隐性偏好。**每分都有出处。**

**权衡**：相比纯 LLM 多了结构化和比对步骤，延迟略增，但换来可解释性与稳定性。向量匹配留作 P2 语义增强。

---

### 决策 2：JD 结构化（对称 job_profile）

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| JD 当纯文本，直接丢给 LLM 比对 | 简单 | 不可追溯、每次比对都要重读全文 | 不选 |
| JD 先结构化成 job_profile，再与画像对齐比对 | 可解释、可复用、对称美 | 多一次 LLM 调用 | ✅ 选择 |

**最终选择**：JD 结构化为 job_profile

**理由**："JD 不是一段文本，是一份结构化的'要求画像'。匹配就变成 profile 对 profile 的对齐。" 这复用了简历解析的设计范式，与 user_profile 对称，降低认知负担。

**权衡**：多一次 LLM 调用、多一个失败点（用重试缓解），但可解释性与复用性收益更大。

---

### 决策 3：匹配维度划分（四维度）

**最终选择**：技能匹配度 / 经验匹配度 / 学历匹配度 / 软技能匹配度

**理由**：
- 覆盖 JD 绝大多数要求类型，且彼此正交、易讲清
- 天然适配雷达图可视化，用户一眼看到强弱项
- 每个维度都有明确的比对来源（技能→技能集、经验→工作经历、学历→教育、软技能→软技能要求）

**权衡**：四维度是经验划分，未来可按行业扩展（如增加"行业背景"维度），维度设计为可扩展。

---

### 决策 4：差距分析（Gap 四分类与闭环接口）

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 只输出"匹配/不匹配"项 | 简单 | 无法指导行动 | 不选 |
| Gap 四分类 + 应对建议 | 可行动、对齐产品、闭环 | 需设计分类与建议 | ✅ 选择 |

**最终选择**：Gap 四分类，对齐产品方案定义

| Gap 类型 | 举例 | 下游（简历优化）如何消费 |
|----------|------|--------------------------|
| 硬技能差距 | 缺 Kafka、经验少 1 年 | 诚实呈现 + 放大相关项 + 转移焦点 |
| 软技能表述弱 | "沟通能力强"太空泛 | STAR 改写 + 数据化成果 |
| 隐性偏好缺位 | 无大厂背景 | 挖掘可类比的高质量经历对冲 |
| 红线预警 | 学历卡线 / 年龄 | 提前预警，简历策略调整 |

**理由**：把"匹配"从"打分"升级为"可行动的诊断"。每行直接对应简历优化的一条改写规则——**想清楚 Gap 的 schema，等于想清楚了简历优化模块一半的输入。**

**权衡**：分类与建议依赖 LLM 质量，用样本调优 + 置信度标注缓解。

---

### 决策 5：匹配可解释性（依据溯源 + 置信度复用）

**最终选择**：每个得分点附 JD 原文出处 + 画像对应内容 + 判定理由；复用简历解析的置信度范式。

**实现逻辑**：
```
每个 matched_item / gap 都包含：
  - requirement:   JD 要求（来自 job_profile）
  - jd_evidence:   JD 原文片段
  - profile_evidence: 画像中的对应内容
  - status:        satisfied / partial / missing
  - confidence:    该判定的置信度（含画像字段置信度传导）
```

**理由**：面试官必问"75 分凭啥可信"。两条腿：依据溯源（可追溯）+ 置信度（画像字段置信度 + JD 解析置信度传导）。**置信度计算模块在简历解析里已建好，JD 匹配直接复用同一套范式——"同一套质量评估体系贯穿全链路"。**

**权衡**：依据与置信度增加输出体积，但这是可信度的核心，不可省。

---

### 决策 6：数据模型（混合：标量拆列 + 列表 JSON）

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 全 JSON blob（整存一个 TEXT） | 最快、可演进 | 不能 SQL 过滤/统计 | 不选 |
| 全关系表（画像 6 表 + 匹配 3 表 = 9 表） | 可 group by 统计 | 模型/迁移/序列化工作量大 | 不选 |
| 混合（标量/固定维度拆列，不定长列表用 JSON） | 兼顾查询与演进 | 列表内容不能直接 SQL 过滤 | ✅ 选择 |

**最终选择**：混合模型，2 张新表

```
user_profiles (1:1 → users)
  ├─ 标量列：name, email, phone, location, 各求职偏好, quality_score
  └─ detail_json：教育/工作/项目/技能/语言/目标岗位（不定长列表）

jd_match_results (N:1 → users)
  ├─ 标量列：overall_score, skill_score, experience_score,
  │          education_score, soft_skill_score（固定维度）
  ├─ jd_text：原始 JD（留痕可复算）
  ├─ job_profile_json：解析出的要求画像
  └─ gaps_json：Gap 清单（喂下游）
```

**理由**：按访问模式建模——常查的标量和固定维度（总分、四维度）拆列建索引，会演进的不定长列表（教育、工作、Gap、JD 要求）存 JSON。**"画像/Gap 这些半结构化、会演进的东西存 JSON；要统计的总分维度拆列——兼顾查询性和演进性。"**

**权衡**：列表内容（如"用户最常缺哪些技能"）不能一条 SQL 出来，需应用层解析。若后续确有统计需求，再针对热点列表拆关系表。

**分层说明**：`users` 表存账户信息（注册名/邮箱），`user_profiles` 存求职档案（简历解析画像），两层职责分离，不冲突。

---

### 决策 7：画像持久化归属

**选项对比**：

| 选项 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 归「简历解析」变更 | 画像能力的延伸 | 该变更已臃肿（113/191） | 不选 |
| 归本变更（作为前置） | 一条线推进、依赖就近 | 变更内含一个基建任务 | ✅ 选择 |
| 单独「画像持久化」变更 | 边界最干净 | 多一个变更切换 | 不选 |

**最终选择**：归本变更，作为区块一前置

**理由**：JD 匹配直接依赖画像存取，就近实现减少跨变更协调。变更内部用**区块一（前置：画像持久化）/ 区块二（核心：JD 匹配）**两段划分，结构上泾渭分明，可追溯。

**权衡**：变更含一个与匹配无关的基建任务，但用区块划分缓解；画像作为全链路共享资产，其持久化接口稳定后，后续模块直接复用。

---

### 决策 8：LangGraph 子图同构

**最终选择**：JD 匹配子图沿用简历解析的同构范式

```
router ──jd_match──▶ jd_intake          收 JD + 校验
                      → jd_quality_check  JD 质量门
                      → jd_parsing        LLM 提取 job_profile（四分类）
                      → profile_load      读 user_profiles（缺失则引导）
                      → match_calc        逐项比对 + LLM 隐性判断 + 加权
                      → gap_analysis      Gap 四分类 + 建议
                      → report_format     写库 + 报告 → END
```

**理由**：与 `profile.py` 的七节点同构——同样的"输入校验 → 质量门 → 结构化提取 → 计算 → 格式化"骨架，同样用条件边处理失败分支。**"每加一个能力就是加一个同构子图，架构成本趋近于零。"**

**权衡**：节点数多，但每个职责单一、可独立测试、可单独跳过/重试。

---

### 决策 9：同步 API + 前端分阶段进度

**最终选择**：MVP 同步 API（沿用简历解析模式），前端分阶段进度提示。

**理由**：JD 匹配端到端 15-25 秒，演示场景可接受。前端按"解析 JD → 提取要求 → 比对画像 → 生成报告"分阶段提示。架构保留异步/SSE 升级空间。

**权衡**：牺牲部分体验（等待），换取实现简单，与现有模式一致。

---

### 决策 10：评分权重与红线惩罚

**最终选择**：四维度加权 + 红线惩罚，权重可配置。

```
初始权重（经验值，可配置）：
  技能 0.4 + 经验 0.3 + 学历 0.15 + 软技能 0.15 = 总分

红线惩罚：
  任一红线项未满足 → 总分 × 0.7 且封顶 60，并醒目预警"存在硬性门槛不满足"
```

**理由**：
- 技能权重最高（JD 最看重且最可量化）
- 红线是硬门槛，未满足应显著拉低分数并预警，而非混在加权里被稀释
- 权重外置为配置，便于按样本调优

**权衡**：权重与惩罚系数是经验值，需用多份 JD 样本校准。


## 与后续功能的集成（闭环接口）

### 画像如何被 JD 匹配使用
```
user_profiles（画像）+ jd_text → JD 子图 → 匹配报告 + Gap 清单
```

### Gap 清单如何喂给简历优化（闭环）
```
jd_match_results.gaps_json  ──▶  简历优化模块的输入
  每个 gap = { type, requirement, current_state, suggestion, severity }

简历优化据此：
  • hard_skill gap  → 强化相关项目、转移焦点
  • soft_skill gap  → STAR 改写、数据化
  • implicit gap    → 挖掘类比经历对冲
  • redline gap     → 策略性呈现 + 预警
```

**这是闭环的关键衔接点**：JD 匹配的 Gap 结构 = 简历优化的输入契约。定义清楚，两个模块解耦又连贯。

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| JD 四分类不准确 | 后续比对失真 | 中 | 结构化输出约束 + 样本调优 + 置信度标注 |
| 隐性偏好判断主观 | 用户质疑结果 | 中 | 附判断理由 + 低置信度"待确认"标注 |
| 匹配权重不合理 | 总分失真 | 中 | 权重可配置，用多份 JD 样本校准 |
| LLM 调用失败/超时 | 流程中断 | 中 | 指数退避重试 + 友好降级 + 保留 JD |
| 画像质量低拖累匹配 | 结果不可信 | 中 | 画像就绪性检查 + 低置信度项标注 |
| 端到端延迟较长 | 体验下降 | 低 | 分阶段进度提示 + 同步可接受 |

## 技术选型总结

| 层级 | 选择 | 理由 |
|------|------|------|
| 匹配算法 | 混合式（结构化 + 程序比对 + LLM） | 可解释、稳定 |
| JD 结构化 | 对称 job_profile（四分类） | 复用解析范式、可追溯 |
| 数据模型 | 混合（标量拆列 + 列表 JSON） | 兼顾查询与演进 |
| 持久化 | SQLAlchemy + SQLite（复用现有基建） | 与 auth 层一致 |
| 框架 | LangGraph 同构子图 | 解耦、可扩展、可讲 |
| API | FastAPI 同步 | 与现有模式一致 |
| 前端 | Vue 3 + 雷达图 | 与项目栈一致 |

## 面试讲解要点

1. **为什么用混合式而不是纯 LLM 打分或向量匹配？**
   - 核心矛盾是可解释性。用户要"为什么 75、差在哪"
   - 程序比对做确定性的硬技能匹配，LLM 只判规则判不了的隐性偏好
   - 向量匹配留作 P2 语义增强，MVP 不堆料

2. **为什么 JD 也要结构化？**
   - "JD 不是文本，是结构化的要求画像"——与 user_profile 对称
   - 匹配 = profile 对 profile 的对齐，复用简历解析范式

3. **为什么 Gap 要四分类？**
   - 对齐产品方案的"硬技能/软技能/隐性/红线"四类要求
   - 每类 Gap 直接对应简历优化的一条改写规则——Gap 结构就是闭环接口

4. **为什么用混合数据模型（拆列 + JSON）？**
   - 按访问模式建模：常查的总分维度拆列，会演进的经历/Gap 存 JSON
   - 兼顾 SQL 查询性与 schema 演进性

5. **可解释性怎么保证？**
   - 每个得分点附 JD 原文 + 画像依据 + 理由
   - 复用简历解析的置信度范式，低置信度项标注"待确认"
   - "同一套质量评估体系贯穿全链路"

6. **为什么画像持久化放在这个变更里？**
   - JD 匹配直接依赖画像存取，就近实现
   - 识别出画像是全链路共享资产，持久化接口稳定后下游复用

7. **架构上的复用优势？**
   - JD 匹配子图与简历解析子图同构（同骨架、同条件边范式）
   - "每加一个能力就是加一个同构子图，架构成本趋近于零"
