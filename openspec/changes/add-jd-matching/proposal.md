# Proposal: JD 匹配分析

## Why（为什么需要）

### 当前痛点
用户建立画像后，最迫切的问题是"我这个条件，到底适合投哪些岗、差在哪里"。市面上的工具要么只帮"改简历"、要么只"模拟面试"，没有一个能在投递前给出**可解释的匹配诊断**。用户盲投、海投，简历与岗位错配，转化率低。

### 产品价值
**JD 匹配分析**是求职 Copilot MVP 闭环的**驱动中枢**：

1. **承上**：消费第一环产出的个人画像，让"建画像"这件事产生实际价值
2. **启下**：输出的差距清单（Gap）直接喂给简历优化模块，构成闭环接口
3. **核心价值感知点**：产品方案明确"Onboarding 后立即引导体验 JD 匹配，让用户第一时间看到差距分析"——这是用户留下来的关键钩子
4. **差异化**：从"给个匹配分数"升级为"可解释、可行动的诊断"——每分有出处、每个 Gap 有建议

### 战略定位
JD 匹配把产品从"单点工具"推向"全链路教练"。它把画像（用户有什么）和 JD（岗位要什么）对齐，输出的不是冷冰冰的分数，而是"差在哪、怎么补、简历怎么改"的行动指南。

## What Changes（做什么变更）

### 新增能力
1. **jd-matching（JD 匹配分析）**
   - JD 粘贴输入与基本校验
   - JD 结构化解析：拆解为四类要求（硬技能 / 软技能 / 隐性偏好 / 红线项）
   - 混合式匹配：结构化要求程序化逐项比对 + 隐性偏好 LLM 综合判断 + 加权汇总
   - 四维度评分：技能 / 经验 / 学历 / 软技能
   - 差距分析（Gap）：四分类 + 应对建议，作为简历优化的输入契约
   - 可解释性：每个得分点附 JD 原文与画像依据 + 置信度
   - 匹配结果持久化：支持历史回看与复算

### 落地能力
2. **user-profile（个人画像持久化）**
   - 将既有但未实现的画像持久化真正落地到数据库
   - 改造简历解析后的画像存取（保存 / 读取 / 更新 / 删除），按用户维度维护
   - 作为 JD 匹配的前置依赖：JD 匹配的"画像加载"环节依赖此能力

### 系统变更
- **LangGraph 状态机扩展**：新增 JD 匹配子图（intake → quality → parsing → profile_load → match_calc → gap_analysis → report）
- **State 扩展**：新增 `jd_text`、`job_profile`、`match_result`、`gaps`、`match_confidence`、`match_status`、`result_id` 等字段
- **API 新增**：
  - `POST /api/jd/match`（提交 JD 文本，执行匹配）
  - `GET /api/jd/history`（查询当前用户的历史匹配）
  - `GET /api/jd/results/{id}`（查看某次匹配详情）
- **数据层新增**：
  - `user_profiles` 表（画像持久化）
  - `jd_match_results` 表（匹配结果持久化）
- **前端组件新增**：
  - `JdMatcher.vue`（JD 匹配主页面）
  - `JdInput.vue`（JD 粘贴输入与校验）
  - `MatchReport.vue`（匹配报告）
  - `ScoreRadar.vue`（四维度雷达图）
  - `GapList.vue`（Gap 清单展示）
  - `RedlineAlert.vue`（红线项预警）

## Capabilities（能力清单）

### jd-matching（JD 匹配分析）
**能力描述**：将用户粘贴的 JD 解析为结构化"要求画像"，与用户个人画像混合比对，输出可解释的匹配度评分与差距清单。

**核心流程**：
```
JD 文本 → 结构化解析(job_profile 四分类)
       → 加载用户画像
       → 逐项程序比对 + LLM 隐性判断 → 四维度得分 → 加权总分
       → 差距分析(Gap 四分类 + 建议)
       → 持久化 + 报告输出
```

**四类要求**：硬技能、软技能、隐性偏好、红线项（对齐产品方案定义）

**四维度评分**：技能匹配度、经验匹配度、学历匹配度、软技能匹配度

**Gap 四分类**：硬技能差距、软技能表述弱、隐性偏好缺位、红线预警

### user-profile（个人画像持久化）
**能力描述**：将简历解析产出的个人画像持久化到数据库，按用户维度维护，供全链路下游能力读取。

**核心行为**：保存（首次/更新，按用户唯一）、读取、删除、不定长列表无损存取。

## Impact（影响分析）

### 用户体验影响
**正面影响**：
- 投递前获得可解释的匹配诊断，降低盲投
- 差距清单 + 建议，给出明确行动方向
- 历史匹配可回看，支持横向对比多个岗位

**潜在风险**：
- 匹配度偏低可能打击用户信心 → 缓解：强调"可补强的 Gap"而非单纯低分，红线项单独提示
- LLM 隐性判断可能主观 → 缓解：附判断理由，低置信度项标注"待确认"

### 技术影响
**依赖复用**：复用已有的 LLM 配置、结构化输出、重试机制、置信度计算、SQLAlchemy 基建，无需引入新依赖。

**性能影响**：
- JD 解析 + 隐性判断需 1-2 次 LLM 调用，端到端预计 15-25 秒
- MVP 采用同步 API + 前端分阶段进度提示（沿用简历解析模式）

**架构影响**：
- LangGraph 新增一个与简历解析**同构**的子图（输入校验 → 质量门 → 结构化提取 → 计算 → 格式化）
- 引入画像与匹配结果两张持久化表，数据模型采用混合策略（标量拆列 + 不定长列表 JSON）
- Gap 清单成为连接简历优化模块的接口契约

### 开发影响
**工作量估算**：
- 后端：5-6 天（数据层与画像持久化 1.5 天、JD 解析与匹配服务 2 天、LangGraph 子图与 API 1.5 天、重试与降级 0.5 天）
- 前端：3-4 天（JD 输入、报告、雷达图、Gap 列表、红线提示、历史）
- Prompt 调优：1-2 天（JD 四分类、隐性判断、Gap 建议）
- 测试与打磨：2 天（多 JD 样本测试、置信度校验、边界处理）
- **总计：11-14 天**

**技术风险**：
- JD 四分类准确性 → 缓解：结构化输出约束 + 样本调优 + 置信度标注
- 隐性偏好判断主观性 → 缓解：附理由、低置信度标注
- 匹配权重需调参 → 缓解：权重可配置，先用经验值再据样本调整

## Success Criteria（成功标准）

### 功能验收
- [ ] 能粘贴 JD 并完成结构化解析（四分类）
- [ ] 画像缺失时正确引导用户先建画像
- [ ] 能输出四维度得分与加权总分
- [ ] 硬技能逐项比对结果准确（满足/部分/未满足）
- [ ] 隐性偏好有 LLM 判断及理由
- [ ] Gap 清单按四分类输出且附建议
- [ ] 红线项单独醒目提示
- [ ] 匹配结果持久化，可查历史与复算
- [ ] 画像持久化可正常存取（保存/读取/更新/删除）

### 质量验收
- [ ] 每个得分点有 JD 原文 + 画像依据（可解释）
- [ ] 低置信度项有"待确认"标注
- [ ] LLM 失败有重试与友好降级
- [ ] Gap 清单结构可被简历优化模块直接消费

### 用户体验验收
- [ ] 用户能在 1 分钟内粘贴 JD 看到匹配报告
- [ ] 报告维度清晰（雷达图 + Gap 分组）
- [ ] 知道下一步该改什么（Gap 建议 → 简历优化入口）
